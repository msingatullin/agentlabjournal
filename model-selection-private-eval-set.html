Почему собственного eval-набора недостаточно заменить лидербордом

Чтение: до 12 минут Уровень: с нуля Обновлено: 25 ноября 2026

Публичный лидерборд помогает составить длинный список кандидатов, но почти никогда не отвечает на главный продуктовый вопрос: какая модель лучше справится именно с вашими запросами, в нужном формате, с приемлемыми затратами и задержкой. Для этого нужен приватный eval-набор — небольшая, но репрезентативная выборка реальных задач.

В этой статье разберём, как собрать набор из 50–100 запросов, зафиксировать ожидаемый результат, проверить схему ответа, качество, стоимость и latency, а затем принять решение, которое можно воспроизвести после смены модели или промпта.

Почему рейтинга недостаточно

Лидерборды полезны для общего сравнения, но их результаты зависят от методики, набора задач, версии модели и правил подсчёта. Даже высокий результат не гарантирует, что модель:

  • правильно обработает ваши типичные формулировки;
  • вернёт ответ в требуемой JSON-схеме;
  • сохранит нужные поля при неполных или неоднозначных данных;
  • уложится в допустимую задержку;
  • останется выгодной при вашем объёме запросов.

Например, модель может быть сильной в общем рассуждении, но часто добавлять поясняющий текст вокруг JSON. Для чат-интерфейса это может быть приемлемо, а для автоматической обработки — ошибкой. Это не утверждение о конкретной модели, а типичная причина, по которой общий рейтинг расходится с поведением в продукте.

Что должно быть в приватном eval-наборе

Хороший набор — это не коллекция самых красивых примеров. Он должен отражать реальный поток запросов и включать как обычные случаи, так и ситуации, где система чаще всего ошибается.

Минимальная структура одной записи

{
  "id": "case-001",
  "input": "Текст реального запроса без персональных данных",
  "category": "обычный сценарий",
  "expected": {
    "must_include": ["поле_1", "поле_2"],
    "must_not_include": ["выдуманное утверждение"],
    "format": "json"
  },
  "risk": "medium",
  "source": "обезличенный лог",
  "review_notes": "Что считать хорошим результатом"
}

Поля source и review_notes нужны для внутренней работы. Они помогают понять происхождение примера и не потерять критерий проверки. В опубликованный или внешний набор нельзя помещать секреты, токены, персональные данные и исходные клиентские сообщения без разрешения.

Шаблон набора на 50–100 запросов

Начните с 50 запросов, если нужно быстро сравнить кандидатов. Увеличьте набор до 100, если в продукте несколько существенно разных сценариев или результаты близки. Ниже — пример распределения; это шаблон, а не универсальная норма.

Группа Доля Что включить
Обычные запросы 40% Наиболее частые формулировки из обезличенных логов
Сложные случаи 20% Длинный контекст, несколько условий, неоднозначность
Ошибочные входы 15% Пропуски, неверный тип данных, пустые значения
Критичные сценарии 15% Случаи, где неверный ответ особенно дорог или опасен
Регрессии 10% Примеры прошлых ошибок и исправленных багов

При наборе из 50 запросов округлите доли до целых значений. Если продукт ещё не запущен, используйте синтетические примеры, но явно пометьте их как синтетические и пересоберите набор после появления реального трафика.

Шаг 1. Соберите и обезличьте запросы

Выберите период, который отражает обычную работу продукта. Не берите только самые новые, самые лёгкие или самые проблемные обращения. Удалите имена, телефоны, адреса, токены, идентификаторы заказов и любые другие данные, по которым можно узнать пользователя.

Сохраните отдельную таблицу соответствий только при наличии обоснованной необходимости и защищённого хранилища. Для самого eval-набора достаточно обезличенной версии.

Безопасная проверка файла перед публикацией может выглядеть так:

rg -n -i 'api[_-]?key|token|password|secret|bearer|пароль|телефон|email' eval.jsonl

Команда только ищет потенциальные совпадения и ничего не удаляет. Она не заменяет ручную проверку: секреты могут иметь другой формат, а обычный текст может совпасть с ключевым словом.

Шаг 2. Зафиксируйте контракт ответа

До запуска моделей опишите, каким должен быть результат. Для каждого кейса зафиксируйте обязательные поля, допустимые значения, правила для пустых данных и запрещённые утверждения. Это превращает размытое «ответ выглядит хорошо» в проверяемый контракт.

Пример контракта:

{
  "type": "object",
  "required": ["answer", "confidence"],
  "properties": {
    "answer": {"type": "string"},
    "confidence": {
      "type": "string",
      "enum": ["low", "medium", "high"]
    }
  },
  "additionalProperties": false
}

Если схема нужна только для автоматической обработки, проверяйте её строго. Если пользователю важен свободный текст, отделите структурированные поля от пояснения и не смешивайте их в одном неформальном формате.

Шаг 3. Разделите автоматические и экспертные проверки

Автоматические проверки

  • ответ получен без ошибки;
  • JSON разбирается;
  • схема соблюдена;
  • обязательные поля присутствуют;
  • значения имеют допустимые типы;
  • нет запрещённых полей или явных служебных данных;
  • измерены входные и выходные токены, стоимость и время.

Экспертные проверки

  • ответ фактически корректен;
  • он отвечает на поставленный вопрос;
  • не содержит необоснованной уверенности;
  • следует правилам продукта;
  • понятен целевой аудитории.

Для экспертной оценки заранее выберите шкалу. Например, 0 — неприемлемо, 1 — есть существенная ошибка, 2 — пригодно после правки, 3 — готово к использованию. Не меняйте шкалу между запусками.

Шаг 4. Проверьте качество, стоимость и latency

Запускайте всех кандидатов на одном и том же наборе и при одинаковых настройках, насколько это возможно. Зафиксируйте дату, идентификатор модели, системный промпт, параметры генерации, лимит токенов и версию проверяющего кода.

Минимальная строка результата может иметь такой вид:

{
  "case_id": "case-001",
  "model": "model-id",
  "schema_valid": true,
  "quality_score": 3,
  "input_tokens": 420,
  "output_tokens": 96,
  "cost": null,
  "latency_ms": 1280,
  "error": null
}

Значение cost нельзя выдумывать: подставьте его из актуального тарифа провайдера или из внутреннего биллинга. Если цена не известна, оставьте поле пустым и сравнивайте расход токенов. Latency тоже не сводится к одной цифре: сохраните хотя бы среднее значение и высокий перцентиль, например p95, если данных достаточно.

Не объединяйте все метрики в один магический балл без объяснения. Продукту может быть важнее схема и p95, а исследовательскому прототипу — качество. Сначала задайте минимальные пороги, затем сравнивайте кандидатов среди тех, кто их проходит.

Шаг 5. Проверьте воспроизводимость

Повторите запуск хотя бы на небольшой части набора. Если ответы нестабильны, один прогон может случайно завысить или занизить результат. Для каждой модели сохраните сырые ответы отдельно от агрегированных метрик.

Перед повторным запуском проверьте:

  • не изменился ли набор входных данных;
  • не добавились ли скрытые примеры в промпт;
  • не перепутались ли единицы измерения времени;
  • не были ли пропущены ошибки API;
  • одинаково ли обработаны пустые и некорректные ответы.

Сам eval-набор тоже нужно версионировать. Изменение критерия или удаление сложного кейса может сделать новый результат несопоставимым со старым.

Как принять решение о модели

Составьте короткую таблицу решения. В ней должны быть не только средние оценки, но и провалы по критичным сценариям.

Проверка Минимум Модель A Модель B
Валидная схема Не ниже заданного порога Заполнить Заполнить
Среднее качество Заданный балл Заполнить Заполнить
Критичные ошибки Не более допустимого числа Заполнить Заполнить
Стоимость запроса Бюджет продукта Заполнить Заполнить
Latency p95 Требование интерфейса Заполнить Заполнить

Если одна модель выигрывает по качеству, а другая — по цене и задержке, это не обязательно требует единственного победителя. Можно назначить маршрутизацию: сложные запросы отправлять одному кандидату, обычные — другому. Такое решение нужно проверять на полном потоке и отдельно учитывать усложнение эксплуатации.

Типовые ошибки

Набор слишком маленький или однородный

Десять похожих запросов не показывают поведение на редких сценариях. Добавьте разные категории, источники ошибок и примеры с пропущенными данными.

Критерии появились после ответа модели

Если оценивать результат по новым правилам, сравнение становится субъективным. Сначала зафиксируйте критерии, затем запускайте кандидатов.

Проверяется только текст

Красивый ответ может быть непригоден для программы из-за неверной схемы, лишних полей или нестабильного формата. Структурные проверки должны быть отдельным обязательным этапом.

Среднее скрывает провалы

Высокое среднее качество не компенсирует редкую, но критичную ошибку. Смотрите разбивку по категориям и отдельный список провальных кейсов.

В набор попали секреты

Логи нельзя автоматически считать безопасными. Обезличьте их, ограничьте доступ и проверьте содержимое перед сохранением или передачей.

Ограничения подхода

Приватный eval-набор не делает оценку абсолютно объективной. Он наследует ошибки выборки, может не покрывать будущие сценарии и не заменяет наблюдение за системой после релиза. Экспертные оценки тоже требуют согласованных правил и периодической проверки согласия между оценщиками.

Публичные рейтинги при этом не бесполезны. Они помогают найти кандидатов, понять общий контекст и заметить модели, которые стоит проверить. Но финальный выбор должен опираться на данные продукта: реальные запросы, допустимый риск, стоимость и latency.

Итоговый чек-лист

  1. Соберите 50–100 обезличенных запросов из реальных сценариев.
  2. Разделите их на обычные, сложные, ошибочные и критичные случаи.
  3. Опишите ожидаемый результат и схему до запуска моделей.
  4. Добавьте автоматические проверки формата и экспертную оценку качества.
  5. Сохраните стоимость, токены, latency и ошибки каждого запуска.
  6. Проверьте повторяемость на части набора.
  7. Сравнивайте модели по порогам и разбивке, а не только по одному среднему баллу.
  8. Версионируйте набор и пересматривайте его после изменений продукта.
