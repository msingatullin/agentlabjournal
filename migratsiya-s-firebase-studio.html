Как перенести приложение из Firebase Studio до закрытия среды

Время чтения: до 12 минут Уровень: с нуля Результат: проект сохранён и запускается вне Firebase Studio

Если рабочая среда перестанет быть доступной, код и настройки, которые остались только внутри неё, могут оказаться недоступны. Поэтому перенос лучше выполнить заранее: сохранить исходники в репозитории, установить зависимости на своём компьютере, проверить сборку и отдельно убедиться, что авторизация и публикация работают без Firebase Studio.

Важно. Команды ниже — шаблон процесса. Имена каталогов, скрипты и переменные зависят от конкретного проекта. Перед запуском посмотрите файлы README.md и package.json, если они есть.

Что нужно подготовить

До начала переноса убедитесь, что у вас есть:

  • доступ к рабочему пространству Firebase Studio;
  • локальный компьютер с Git и нужной версией среды выполнения проекта;
  • репозиторий, куда можно отправить исходный код;
  • доступ к проекту Firebase и его настройкам;
  • резервная копия важных конфигураций, которые разрешено хранить вне среды.

Секреты, приватные ключи и файлы с паролями не помещайте в Git. Если в проекте есть файл .env, проверьте, что он исключён через .gitignore. Сохраните только перечень необходимых переменных, например в отдельной защищённой заметке.

Шаг 1. Найдите корень проекта

В Firebase Studio откройте папку, в которой находятся исходники приложения. Корнем проекта обычно считается каталог с одним или несколькими файлами: package.json, vite.config.*, next.config.*, firebase.json, src/ или app/.

Проверьте, что в копию попадают не только файлы интерфейса, но и:

  • конфигурация сборки;
  • правила Firebase, если они используются;
  • функции или серверная часть;
  • миграции и схемы базы данных;
  • README.md с инструкциями запуска.

Шаг 2. Создайте локальную копию

Если проект уже подключён к Git, сначала проверьте состояние и историю:

git status
git log --oneline -5

Если Git ещё не настроен, выполните команды из корня проекта:

git init
git add .
git status
git commit -m "Save project before Firebase Studio shutdown"

Команда git status нужна для проверки списка файлов перед фиксацией. Если среди них видны .env, ключи, сертификаты или другие секреты, остановитесь: добавьте их в .gitignore, удалите из индекса и только затем создавайте коммит.

Пример минимального .gitignore для JavaScript-проекта:

node_modules/
dist/
build/
.env
.env.*
!.env.example

Файл .env.example может содержать только названия переменных без значений: 

VITE_FIREBASE_API_KEY=
VITE_FIREBASE_AUTH_DOMAIN=
VITE_FIREBASE_PROJECT_ID=

Шаг 3. Перенесите код в удалённый репозиторий

Создайте пустой репозиторий в выбранном Git-сервисе. Если сервис предлагает автоматически создать README, лицензии или шаблон, для уже готового проекта удобнее оставить репозиторий пустым.

Подставьте адрес своего репозитория вместо значения в угловых скобках:

git branch -M main
git remote add origin <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
git push -u origin main

После отправки откройте репозиторий в браузере и убедитесь, что там есть исходники, конфигурации и история коммитов. Не публикуйте секреты даже в закрытом репозитории без необходимости: доступ к нему может быть изменён позже.

Шаг 4. Запустите приложение вне Firebase Studio

Склонируйте проект в отдельный каталог и перейдите в него:

git clone <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
cd <ИМЯ_КАТАЛОГА>

Установите зависимости тем способом, который указан в lock-файле:

# если есть package-lock.json
npm ci

# если есть только package.json
npm install

Если проект использует другой менеджер пакетов, следуйте его lock-файлу: например, pnpm-lock.yaml требует pnpm, а yarn.lock — Yarn. Не смешивайте lock-файлы без причины.

Посмотрите доступные скрипты:

npm run

Затем запустите скрипт разработки. Его название чаще всего — dev, но точное значение нужно взять из раздела scripts в package.json: 

npm run dev

Откройте адрес, который вывел терминал. Проверьте главную страницу, переходы между маршрутами и отсутствие ошибок в консоли браузера.

Шаг 5. Проверьте production-сборку

Сборка должна проходить в чистой локальной копии, а не только в Firebase Studio:

npm run build

Если скрипт называется иначе, используйте имя из package.json. После успешной сборки проверьте, какая команда запускает готовый результат: 

npm run start

Результат сборки не должен зависеть от случайных файлов, оставшихся в рабочем пространстве. Если сборка требует переменные окружения, создайте локальный файл на основе .env.example, но не добавляйте его в Git.

Шаг 6. Проверьте авторизацию

Авторизация часто ломается после переноса из-за неправильных переменных или ограничений домена. Проверьте минимум такие сценарии:

  1. открытие страницы входа;
  2. вход тестовым способом, который предусмотрен вашим проектом;
  3. выход из аккаунта;
  4. обновление страницы после входа;
  5. доступ к защищённому маршруту без входа;
  6. сообщение об ошибке при некорректных данных.

Если вход не работает, сравните имена переменных с кодом приложения и настройками Firebase. Для локального запуска проверьте разрешённые домены в настройках провайдера авторизации. Не копируйте секретные значения в статью, issue или публичный коммит.

Шаг 7. Проверьте публикацию

Выберите способ публикации, который поддерживает ваш проект: Firebase Hosting, другой хостинг, сервер или собственный pipeline. Сначала выполните публикацию в тестовой среде, если она предусмотрена.

Перед публикацией проверьте:

  • какая папка указана как каталог готовых файлов;
  • нужен ли режим single-page application с перенаправлением маршрутов;
  • передаются ли переменные окружения на этапе сборки;
  • разрешён ли домен опубликованного приложения для авторизации;
  • не попадают ли исходники и конфигурационные секреты в публичную раздачу.

После публикации откройте приложение в приватном окне браузера и повторите основные сценарии: загрузка страницы, переходы, вход, выход, обновление защищённой страницы и обработка ошибки.

Итоговая проверка перед закрытием среды

Перенос можно считать завершённым, если выполнены все пункты:

  • код находится в удалённом репозитории;
  • последний коммит виден в истории;
  • в репозитории нет секретов и локальных зависимостей;
  • проект клонируется в новый каталог;
  • зависимости устанавливаются штатной командой;
  • локальный запуск работает вне Firebase Studio;
  • production-сборка завершается без ошибок;
  • авторизация проходит основные сценарии;
  • опубликованная версия открывается и работает;
  • README объясняет установку, запуск, сборку и необходимые переменные.

Типовые ошибки

После клонирования не найден скрипт запуска

Проверьте раздел scripts в package.json. Команда могла называться не dev, а, например, start или иметь отдельный скрипт для конкретного фреймворка.

Сборка проходит в Studio, но не локально

Сравните версии Node.js и менеджера пакетов, затем проверьте переменные окружения. Также убедитесь, что локальная команда запускается из корня проекта.

Приложение открывается, но вход не работает

Проверьте конфигурацию Firebase, разрешённый домен и наличие обязательных переменных. Ошибка может быть связана не с кодом, а с настройками проекта или окружения.

После публикации внутренние маршруты дают 404

Для одностраничных приложений хостингу может понадобиться правило, которое направляет неизвестные маршруты на главный HTML-файл. Точная настройка зависит от выбранного хостинга.

В репозитории оказался секрет

Немедленно отзовите или замените такой ключ в соответствующем сервисе. Простого удаления файла новым коммитом недостаточно: значение может остаться в истории Git.

Ограничения этого переноса

Копирование исходников не переносит автоматически внешние ресурсы: данные базы, пользователей, правила доступа, домены, секреты, настройки OAuth и опубликованные файлы. Их нужно проверить отдельно в используемых сервисах. Если приложение зависит от серверных функций или фоновых задач, перенесите и проверьте их по отдельному плану.

Если вы не уверены, какие ресурсы используются, начните с инвентаризации: найдите импорты Firebase, файлы конфигурации, переменные окружения и команды деплоя. Зафиксируйте найденное в README, чтобы следующий запуск не зависел от памяти автора проекта.
