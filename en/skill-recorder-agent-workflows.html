Microsoft Skill Recorder: Turning a Screen Recording into a Reusable Agent Skill

A repeatable operation is often easier to demonstrate than to describe. Microsoft Skill Recorder captures that demonstration, turns it into an ordered procedure, and gives you an editable SKILL.md rather than an opaque recording. The useful workflow is not “record and trust the model.” It is record, inspect, edit, and replay against a safe test case.

Updated: 28 November 2026 Reading time: 25 minutes Level: Intermediate

What this workflow solves

Suppose an operations team repeatedly prepares a weekly status report. The task involves opening a source page, copying selected values, transforming them, saving a file, and notifying a channel. A written request such as “prepare the report” leaves too much implicit: which page, which fields, which naming convention, and which validation checks?

A screen recording preserves the order and context of one real run. Skill Recorder can analyze that run and produce a candidate skill that an agent can use later. The candidate is still a draft: it may contain incidental clicks, brittle selectors, private data, or assumptions that were obvious only to the person recording.

Evidence boundary. This article documents the workflow and the checks to perform. The local workspace used to prepare this article contained no site files and no Skill Recorder installation, so this article does not claim that installation or replay was executed here.

What Skill Recorder captures

According to the project README, recording and local processing happen on the computer. When the user chooses analysis, the recorded event timeline, selected screen images, optional narration, and bounded terminal-output excerpts may be sent to the selected AI provider. The exact data boundary depends on the settings and provider configuration in the installed build.

Treat a recording as sensitive working material. Do not record passwords, access tokens, customer records, private URLs, personal messages, or an unredacted terminal containing secrets. Use a disposable test account and synthetic data wherever possible.

The resulting skill is normally a directory with a required SKILL.md file and optional scripts, templates, or references. Microsoft’s agent-skill documentation describes the Markdown file as the instruction layer that tells the agent how to perform the task.

Before you record

Define the operation as a small contract. Write down:

  • Input: what file, page, message, or record starts the task?
  • Output: what artifact or state must exist when it finishes?
  • Constraints: what must not be changed or sent?
  • Success check: how can someone verify the result without watching the recording?
  • Failure response: what should happen if a required field, page, or permission is missing?

For the status-report example, a useful contract might be: “Read the three synthetic metrics in weekly-input.csv, calculate the percentage change, write weekly-status.md, and stop if any metric is missing. Never send the report automatically.”

Keep the recording narrow. Complete one task from a clean starting state, avoid unrelated window switches, and narrate decisions rather than every mouse movement. Say why a field is selected and what makes the result valid.

Installation: use the release instructions for your platform

Skill Recorder’s repository publishes platform-specific, commit-pinned installation commands in its releases and README. Use the latest release instructions rather than copying an unpinned command from an old article. The project has documented native Windows 11 builds for x64 and ARM64; verify the current release notes for other supported platforms before proceeding.

A safe installation sequence is:

  1. Open the project’s official release page.
  2. Choose the release and operating-system instructions that match the machine.
  3. Inspect the command before running it.
  4. Prefer the commit-pinned installer supplied by the release.
  5. Launch Skill Recorder and review its privacy and provider settings.

Example only: the release notes show a PowerShell pattern that assigns a specific commit and downloads that commit’s installer. Do not substitute an arbitrary commit or execute a command you have not inspected. 

$env:SKILL_RECORDER_COMMIT="<release-commit-from-official-notes>"
irm "https://raw.githubusercontent.com/microsoft/skill-recorder/$env:SKILL_RECORDER_COMMIT/install.ps1" | iex

The placeholder is intentional. This article does not hard-code a changing release identifier or claim that the command was executed.

Record a repeatable operation

  1. Open Skill Recorder and create a new recording.
  2. Confirm the recording scope and privacy settings.
  3. Prepare synthetic inputs and a clean destination.
  4. Start recording.
  5. Perform the operation once, slowly enough that the important state changes are visible.
  6. Explain decisions aloud if narration is enabled.
  7. Stop recording only after the output and success check are visible.

During the recording, prefer stable actions. If a command is required, use a safe, reproducible command and avoid embedding secrets in arguments. If the operation normally includes a destructive action, replace it with a dry run or a test destination.

A good recording ends with evidence: the generated file opens, the expected row exists, or the test message appears in a private channel. The agent needs an observable result, not only a sequence of clicks.

Analyze the recording

Choose the analysis action only after reviewing the captured session. Analysis is the point at which selected recording data can leave the machine for processing by the configured provider. Confirm that the timeline, images, narration, and terminal excerpts contain no sensitive information.

The generated analysis should be read as an interpretation of one demonstration. Look for four parts:

  • Intent: what outcome the operation appears to achieve.
  • Ordered steps: the actions the agent should perform.
  • Tool choices: whether a native command, API, browser action, or file operation is preferable.
  • Assumptions: facts inferred from the recording but not guaranteed by the task.

A useful analysis replaces incidental UI actions with durable intent. For example, “click the third row” is weaker than “select the record whose status is Pending.” Keep the concrete click only when no stable alternative exists.

Inspect and edit the generated SKILL.md

Export or open the generated skill in a text editor. Do not treat the generated Markdown as final until a person can explain every step. A minimal structure looks like this: 

---
name: weekly-status-report
description: Create a weekly status report from the approved synthetic input file.
---

# Weekly status report

## Preconditions
- The input file is `weekly-input.csv`.
- The destination is a test workspace.
- Do not send messages or publish the report.

## Procedure
1. Read the input file.
2. Confirm that all required metrics are present.
3. Calculate the percentage change for each metric.
4. Write `weekly-status.md`.
5. Re-open the file and verify the headings and values.

## Stop conditions
- Stop if the input file is missing.
- Stop if a required metric is blank.
- Stop before any external send or publish action.

## Verification
- Confirm that `weekly-status.md` exists.
- Confirm that each metric appears once.
- Report the output path and any skipped step.

Edit the draft around invariants, not around the exact pixels of the recording. Replace private names with roles, hard-coded dates with explicit date rules, and vague completion language with observable checks.

Editing checklist

  • Use a short, descriptive name in the front matter.
  • State the trigger and expected output.
  • Separate preconditions from actions.
  • Mark irreversible operations as requiring confirmation.
  • Add stop conditions for missing data, ambiguity, and permission errors.
  • Remove credentials, tokens, personal data, and customer identifiers.
  • Prefer stable identifiers over screen coordinates.
  • Keep the skill focused on one repeatable operation.

Replay safely

Replay is a test, not a production launch. Use a fresh test directory, synthetic input, and an account with the minimum permissions needed. If the skill can send, delete, publish, or modify records, add a confirmation gate before that step.

  1. Reset the test environment to the documented preconditions.
  2. Run the agent with the edited skill.
  3. Observe each step and capture the output.
  4. Compare the result with the success checks in SKILL.md.
  5. Repeat with one controlled variation, such as a different valid input.
  6. Test at least one failure condition, such as a missing file.

A replay passes only when the result is correct and the agent stops correctly when the task cannot be completed. A skill that produces the right output once but silently proceeds with missing data is not ready for routine use.

Verification record

Keep a small verification record beside the skill. It makes later edits auditable and prevents “it worked once” from becoming the acceptance criterion. 

# Verification record

Date: YYYY-MM-DD
Skill version: 0.1
Input fixture: weekly-input-v1.csv
Expected output: weekly-status.md

Checks:
- [ ] Clean test run completes.
- [ ] Output file exists.
- [ ] Output values match the fixture.
- [ ] Missing-input test stops safely.
- [ ] Ambiguous-input test asks for clarification.
- [ ] No external message is sent.
- [ ] No secret or personal data is present in the skill package.

Record the exact fixture and skill revision used. If the generated workflow changes, repeat the clean run and the failure tests. Do not report a verification result until someone has actually performed the check.

Common failure cases

The generated steps describe clicks instead of intent

This usually means the demonstration contained too little narration or no visible success condition. Edit the skill to identify records by meaning and state the invariant that makes the action correct.

The agent repeats a one-off value

A recording can make a sample date, filename, or customer name look like a rule. Replace it with a parameter or a documented derivation. Add a test using a second valid input.

Replay stops at a changed interface

UI layouts and labels change. Prefer native tools, APIs, command-line interfaces, and semantic identifiers when available. Keep UI-specific instructions as a fallback, and document the version or page state they depend on.

Analysis contains sensitive material

Stop the workflow, remove the exposed material from the draft, and review the provider and recording settings. Re-record with synthetic data if the original capture included credentials or personal information. Do not publish the recording or generated skill while the exposure is unresolved.

The skill succeeds but cannot explain what it changed

Add an output summary and verification step. A reusable skill should report what it read, what it changed, what it skipped, and where the result was written.

Limitations to plan for

  • A recording captures one path; it does not automatically define every valid variation.
  • Generated instructions can contain incorrect assumptions and require human editing.
  • UI replay is vulnerable to layout, permissions, timing, and content changes.
  • Analysis may transmit selected recording data to the configured AI provider.
  • Long or high-resolution recordings consume local storage and processing resources.
  • Skill support differs between Microsoft agent hosts; confirm the target host’s accepted format and packaging rules.
  • Automations with external side effects need separate authorization, monitoring, and rollback decisions.

A practical definition of done

The workflow is complete when a second person can install the required tool, understand the recording boundary, inspect the generated steps, edit the skill without guessing, replay it against a clean fixture, and verify both success and safe failure. The recording is evidence for authoring; the edited SKILL.md is the maintainable artifact.

For current installation syntax and project-specific behavior, consult the Microsoft Skill Recorder repository and its release notes. For the target agent host, check its current skill packaging documentation before treating the skill as portable.
