Why a Private Evaluation Set Beats a Public Leaderboard

A public ranking can tell you which model performs well on someone else’s test. It cannot tell you which model handles your requests, returns your required format, fits your budget, or answers quickly enough for your product. A small private evaluation set gives you evidence that is closer to the decision you actually need to make.

This article presents a repeatable template for a private set of 50–100 examples. The template covers four dimensions: schema compliance, answer quality, cost, and latency. The numbers below are examples of a test design, not measured results. Replace them with values from your own requests and model runs.

The decision a leaderboard cannot make

Imagine that a team needs a model for an assistant that reads support messages and produces a structured triage record. The output must contain a category, urgency, short summary, and a next action. Some messages are incomplete. Some contain irrelevant text. A few contain instructions that should be treated as content rather than as commands.

The team may compare models using a public leaderboard. That ranking may be useful for generating a shortlist, but it does not answer the operational questions:

  • Does the model return valid JSON every time?
  • Does it choose the correct category on the team’s real message types?
  • Does it avoid inventing missing information?
  • How many input and output tokens does each request use?
  • Does the response arrive within the application’s time budget?

A private evaluation set turns those questions into checks that can be rerun after a model, prompt, provider, or decoding setting changes.

What to put in a 50–100-example set

Start with examples that represent the work, not examples that are easy to write. Remove names, email addresses, account numbers, access tokens, and other personal or secret data before storing the set. If the original request cannot be safely retained, create a redacted or synthetic equivalent and mark it as such.

A practical distribution for 50 examples is:

Example group Suggested count What it tests
Common requests 20 Normal task performance
Ambiguous or incomplete requests 10 Clarification and uncertainty handling
Long or noisy requests 8 Context use and instruction priority
Rare but important cases 7 High-impact failure modes
Adversarial or malformed inputs 5 Robustness and safe failure

For 100 examples, keep the categories roughly balanced rather than simply duplicating common requests. The exact mix is an experiment-design choice. Record the reason for each example so that a future editor can tell whether the set still represents the product.

Use a data record that separates facts from judgments

Store one row or JSON object per example. Keep the original request, the expected behavior, and the model output separate. A reference answer can be useful, but it should not be treated as the only acceptable wording when several answers would be correct. 

{
  "id": "triage-001",
  "input": "The replacement part arrived damaged. What should I do?",
  "source": "synthetic",
  "expected": {
    "category": "replacement",
    "urgency": "normal",
    "must_include": ["next step"],
    "must_not_include": ["invented order number"]
  },
  "quality_notes": "A concise explanation and a request for the missing order details are acceptable.",
  "tags": ["common", "missing_context"]
}

The source field distinguishes a redacted production example from a synthetic one. The expected field describes observable requirements. This makes review more consistent than asking a reviewer whether an answer “feels good.”

Check schema compliance first

If your application consumes structured output, begin with schema validation. A fluent answer that cannot be parsed is a failed request for many workflows.

Define the required shape in JSON Schema or the equivalent format supported by your application. For example: 

{
  "type": "object",
  "additionalProperties": false,
  "required": ["category", "urgency", "summary", "next_action"],
  "properties": {
    "category": {
      "type": "string",
      "enum": ["billing", "technical", "replacement", "other"]
    },
    "urgency": {
      "type": "string",
      "enum": ["low", "normal", "high"]
    },
    "summary": {
      "type": "string",
      "minLength": 1
    },
    "next_action": {
      "type": "string",
      "minLength": 1
    }
  }
}

A schema check should record at least three outcomes: valid, invalid, and unavailable. “Unavailable” covers cases where the provider returned no usable response or a transport error occurred. Do not silently count unavailable responses as valid or as quality failures; report them separately.

A minimal validation command might look like this when using a local JSON file and a validator already installed in your environment: 

jsonschema -i output.json schema.json

The command is illustrative. The exact command depends on the validator and language used by your project. The reproducible requirement is to record the schema version, validator version, and result for every example.

Measure quality with explicit criteria

Quality is not one universal score. Define criteria that match the task. For the triage example, a reviewer could score each response on a 0–2 scale:

Criterion 0 1 2
Correct category Wrong Partly justified Correct
Appropriate urgency Unsafe or wrong Debatable Supported by input
Useful next action Missing or misleading Partly useful Clear and actionable
Groundedness Invents facts Minor unsupported detail Uses only supported facts

Define a pass rule before comparing models. One example is: schema valid, no critical error, and a total quality score of at least 6 out of 8. This threshold is a test-design example, not a verified standard. Choose a threshold with the people responsible for the outcome, then keep it fixed during the comparison.

For a first pass, have one reviewer score all outputs and have a second reviewer independently score a smaller sample, such as 10 examples. Discuss disagreements and update the rubric before the next evaluation. Do not present a reviewer score as objective ground truth when the rubric remains ambiguous.

Record cost using the same assumptions

Cost comparisons are only meaningful when the request, output limit, tools, retries, and pricing assumptions are held constant. Do not copy a price into the article or evaluation file unless it has been verified for the provider, region, account, and date of the run.

Record usage fields returned by the provider whenever available: 

{
  "input_tokens": 842,
  "output_tokens": 126,
  "retries": 0,
  "request_status": "success",
  "price_snapshot": "record provider price source and date here"
}

A simple calculation for one request is: 

request_cost =
  (input_tokens / 1_000_000) * input_price_per_million
  + (output_tokens / 1_000_000) * output_price_per_million

The expression is a template. Insert the prices that apply to the run and preserve the source and date of those prices in your internal evaluation record. Include retry costs if retries are part of the production behavior.

Measure latency as a distribution

A single average can hide slow requests. Measure elapsed time from the start of the request until the application receives a complete usable response. Record the timestamp, model identifier, region or deployment context if relevant, timeout, retry count, and whether the response was streamed.

Report the median and a high percentile such as p95 latency. For 50 examples, p95 is sensitive to a single slow request, which is useful but should be described clearly. If your application has a strict deadline, also report the percentage that finishes before that deadline. 

started_at,finished_at,status,input_tokens,output_tokens,latency_ms
2026-11-25T10:00:00Z,2026-11-25T10:00:01Z,success,842,126,1000

The timestamp above is an example record format, not a measured result. Use a monotonic clock for elapsed time in code when possible, and retain wall-clock timestamps only for traceability.

Run the comparison with a fixed configuration

Create one configuration file per model. Keep the system instruction, user-message template, schema, temperature or equivalent decoding settings, maximum output tokens, timeout, and retry policy explicit. 

{
  "model": "MODEL_ID_TO_VERIFY",
  "system_prompt_version": "triage-v3",
  "schema_version": "triage-schema-v2",
  "temperature": 0,
  "max_output_tokens": 300,
  "timeout_seconds": 20,
  "max_retries": 0
}

Run every example against every candidate using the same input files and configuration rules. Save raw responses separately from normalized evaluation rows. A run identifier should connect the configuration, code revision, schema version, and outputs.

At minimum, the normalized result should contain:

{
  "run_id": "2026-11-25-model-a-triage-v3",
  "example_id": "triage-001",
  "model": "MODEL_ID_TO_VERIFY",
  "schema_valid": true,
  "quality_score": 7,
  "critical_error": false,
  "input_tokens": 842,
  "output_tokens": 126,
  "latency_ms": 1000,
  "status": "success"
}

Verify the result before choosing a model

Do not choose a model from one headline number. Verify the raw records and the aggregation logic.

  1. Confirm that every example has one result per candidate.
  2. Check that failed requests were not dropped from the denominator.
  3. Recalculate schema pass rate from raw validation results.
  4. Recalculate quality summaries from the stored rubric scores.
  5. Recalculate cost from recorded token usage and the documented price snapshot.
  6. Inspect latency outliers and confirm that timeouts and retries are visible.
  7. Review all critical failures, even when the aggregate score is high.
  8. Repeat a small sample if outputs are nondeterministic or if the provider documents variable behavior.

A decision table can make the trade-off visible:

Dimension Decision question Evidence to retain
Schema Can the application parse the response? Raw output, schema version, validator result
Quality Does it meet the task rubric? Scores, reviewer notes, critical-error flags
Cost What does one comparable request cost? Token usage, price source, retry count
Latency Does it meet the response-time budget? Elapsed time, timeout, percentile calculation

Common failure cases

The set contains only easy examples

A model can look excellent when every request is short, complete, and unambiguous. Add incomplete, noisy, rare, and adversarial cases. Keep tags so you can see which group causes failures.

The reference answer is treated as the only correct answer

This penalizes valid variation. Use required facts, forbidden claims, and task-specific criteria where wording can vary.

Invalid JSON is repaired before scoring

If production code repairs malformed output, evaluate both the raw response and the repaired result. Otherwise you may hide a reliability problem or fail to measure the actual application behavior.

Cost is compared without output limits

A model allowed to generate twice as much text is not being compared under the same operating conditions. Fix the output limit and record truncation.

Latency is measured from inconsistent points

Decide whether timing includes queueing, network transfer, parsing, retries, and post-processing. Use the same boundary for every candidate.

The set becomes public

A private set can contain sensitive business patterns even after obvious identifiers are removed. Restrict access, avoid secrets, and rotate examples if publication or leakage could change future behavior.

Limitations

Fifty to one hundred examples are enough to expose many practical differences, but they cannot prove universal performance. A small set may miss rare failures, and human scoring may be inconsistent. Provider behavior, model versions, pricing, and service capacity can change after the run.

Treat the evaluation as decision evidence with a scope, date, configuration, and known uncertainty. Add new examples when users report a failure, and rerun the set after material changes to prompts, schemas, tools, models, or application logic.

A compact repeatable template

  1. Collect 50–100 representative, redacted or synthetic requests.
  2. Tag each request by scenario and failure risk.
  3. Define the output schema and version it.
  4. Write a quality rubric with explicit pass and critical-error rules.
  5. Fix model, prompt, schema, decoding, timeout, and retry configuration.
  6. Run every candidate on the same examples.
  7. Store raw outputs, validation results, quality scores, usage, and latency.
  8. Inspect failures and report results by scenario, not only as one average.
  9. Choose the model that meets the required quality and reliability constraints within the cost and latency budget.
  10. Keep the set private, versioned, and updated as the real workload changes.

Public rankings are useful for discovering candidates. A private evaluation set is what lets you defend a model choice against the requests your system actually receives.
