Как безопасно дать MCP-серверу право возвращать заказы Shopify

Безопасное подключение строится вокруг одного принципа: AI-ассистент может подготовить возврат, но не должен самостоятельно завершать финансово значимое действие. Для этого разделите инструменты на чтение и изменение, добавьте серверные ограничения, отдельное подтверждение и неизменяемый журнал событий.

В этой статье MCP (Model Context Protocol) рассматривается как граница между ассистентом и Shopify. MCP-сервер не должен быть «прозрачным прокси» с полным доступом к магазину. Его задача — предоставить небольшой набор явно описанных операций, проверять права на сервере и возвращать ассистенту только те данные, которые нужны для текущего запроса.

Что именно нужно защитить

Запрос «верни заказ» неоднозначен. Он может означать поиск подходящего заказа, расчёт суммы, создание черновика возврата или фактическое проведение возврата. Эти операции имеют разный риск и должны быть разными MCP-инструментами.

Операция Режим Подтверждение
Поиск заказа по разрешённым полям Только чтение Не требуется
Просмотр строк заказа и доступного количества Только чтение Не требуется
Расчёт предварительной суммы возврата Только чтение Не требуется
Создание заявки или черновика возврата Изменение состояния Желательно
Проведение возврата денег Опасное изменение Обязательно

Главная ошибка — выдать один универсальный инструмент вроде shopify_admin_request. В таком дизайне модель сама выбирает endpoint, параметры и момент выполнения. Разделяйте операции на уровне MCP-схемы и повторяйте проверку на сервере: описание инструмента не является механизмом безопасности.

Рекомендуемая модель разрешений

Используйте четыре независимых слоя.

  1. Идентичность сотрудника. MCP-сервер получает подтверждённый идентификатор пользователя, а не имя, названное моделью в тексте.
  2. Роль и область действия. Сервер определяет, может ли сотрудник только просматривать заказы, создавать заявки или проводить возвраты.
  3. Лимиты операции. Ограничиваются магазин, сумма, валюта, количество позиций, допустимые статусы заказа и срок действия подтверждения.
  4. Подтверждение и аудит. Опасная операция выполняется только после явного подтверждения с фиксированным набором параметров и записывается в журнал.

Полезно разделить роли, например, на orders.read, refunds.prepare и refunds.execute. Названия условны: используйте собственную систему ролей, но сохраняйте отдельное право на проведение возврата. Наличие права читать заказ не должно автоматически означать право менять его финансовое состояние.

Шаг 1. Выдайте Shopify минимальный токен

Создайте отдельное приложение или отдельный набор учётных данных для MCP-сервера. Не используйте персональный токен администратора и не передавайте секрет в контекст модели.

Практическая схема:

  • один магазин и один серверный контур на credential;
  • только необходимые scopes Shopify;
  • секрет хранится в менеджере секретов или защищённых переменных окружения;
  • ротация выполняется без вывода значения в логи;
  • доступ к секрету есть только у процесса MCP-сервера.

Если сервер должен только отвечать на вопросы по заказам, начните с режима чтения. Право на возвраты добавляйте отдельным этапом после проверки журналов и проверок авторизации.

Шаг 2. Разделите MCP-инструменты

Ниже — безопасный эскиз контракта. Это пример структуры, а не готовая команда для конкретного MCP-сервера.

{
  "tools": [
    {
      "name": "shopify_order_search",
      "mode": "read",
      "required_role": "orders.read",
      "additional_properties": false
    },
    {
      "name": "shopify_order_return_preview",
      "mode": "read",
      "required_role": "refunds.prepare",
      "additional_properties": false
    },
    {
      "name": "shopify_refund_prepare",
      "mode": "write",
      "required_role": "refunds.prepare",
      "requires_confirmation": true,
      "additional_properties": false
    },
    {
      "name": "shopify_refund_execute",
      "mode": "dangerous_write",
      "required_role": "refunds.execute",
      "requires_confirmation": true,
      "confirmation_ttl_seconds": 120,
      "additional_properties": false
    }
  ]
}

Для каждого инструмента задайте строгую JSON-схему: обязательные поля, допустимые значения enum, максимальные длины строк и запрет неизвестных свойств. Идентификатор заказа должен приниматься в одном ожидаемом формате. Не позволяйте модели передавать произвольный URL, имя метода HTTP или фрагмент запроса к Shopify.

Шаг 3. Ограничьте чтение заказов

Режим только чтения не означает отсутствие риска. Заказы могут содержать персональные и коммерческие данные. Инструмент поиска должен:

  • разрешать только необходимые фильтры;
  • ограничивать размер страницы и общее число результатов;
  • маскировать поля, которые не нужны для задачи;
  • не возвращать секреты, внутренние токены и платёжные реквизиты;
  • проверять, что сотрудник имеет доступ именно к выбранному магазину.

Безопасная команда для локальной проверки конфигурации должна показывать только имена инструментов и режимы:

mcp-server tools list \
  --config ./mcp-shopify.json \
  --fields name,mode,required_role,requires_confirmation

Не используйте команды диагностики, которые печатают весь конфигурационный файл: в нём могут оказаться секреты или заголовки авторизации.

Шаг 4. Введите двухфазный возврат

Для возврата используйте последовательность preview → confirm → execute.

  1. shopify_order_return_preview проверяет заказ, строки, количества, доступный способ возврата и предварительную сумму.
  2. shopify_refund_prepare создаёт короткоживущий объект подтверждения с хешем параметров.
  3. Интерфейс показывает сотруднику заказ, позиции, сумму, валюту, причину и магазин.
  4. Сотрудник явно подтверждает именно этот набор параметров.
  5. shopify_refund_execute принимает только идентификатор подтверждения и повторно проверяет все ограничения.

Не передавайте в финальный вызов только фразу «подтверждаю». Подтверждение должно быть связано с конкретным объектом: заказом, строками, количеством, суммой, валютой и сроком действия. Если любой параметр изменился, старое подтверждение становится недействительным.

mcp-server refund execute \
  --confirmation-id "conf_..." \
  --actor-id "employee_..." \
  --request-id "req_..."

Команда выше иллюстративна. Реальное имя CLI и формат идентификаторов зависят от реализации MCP-сервера. Важно, что сумма и строки не берутся из свободного текста ассистента: сервер загружает их из подтверждённого объекта и сверяет с текущим состоянием заказа.

Шаг 5. Задайте серверные лимиты

Лимиты должны применяться после авторизации и до вызова Shopify. Минимальный набор:

  • разрешённые идентификаторы магазинов;
  • разрешённые роли для каждой операции;
  • максимальная сумма одной операции;
  • максимальное число позиций и количество единиц;
  • разрешённые валюты;
  • запрет частичного возврата без отдельного права;
  • запрет повторного использования confirmation ID;
  • rate limit и дневной лимит для опасных операций;
  • тайм-аут и идемпотентный request ID.

Если политика магазина требует ручной проверки крупных возвратов, сервер должен возвращать состояние approval_required, а не пытаться обойти ограничение через другой endpoint.

Шаг 6. Учитывайте права сотрудников

Права модели и права сотрудника — разные вещи. Модель может предложить действие, но итоговая авторизация должна опираться на серверную сессию сотрудника или на другой проверенный механизм идентичности.

Проверяйте как минимум:

  • кто инициировал запрос;
  • в каком магазине он работает;
  • какая роль активна сейчас;
  • действительно ли роль допускает конкретный тип возврата;
  • не истекла ли сессия или подтверждение;
  • не был ли заказ изменён после предпросмотра.

Нельзя считать достаточным поле actor, переданное моделью в аргументах инструмента. Оно может использоваться для отображения, но не для принятия решения о доступе.

Шаг 7. Настройте аудит

Для каждой операции записывайте отдельное событие. Минимальная запись должна содержать:

{
  "request_id": "req_...",
  "confirmation_id": "conf_...",
  "actor_id": "employee_...",
  "shop_id": "shop_...",
  "tool": "shopify_refund_execute",
  "order_id": "order_...",
  "amount": "100.00",
  "currency": "RUB",
  "result": "success",
  "created_at": "server-generated-time"
}

Не записывайте в журнал access token, полный адрес покупателя и другие поля, которые не нужны для расследования. Для отклонённых запросов фиксируйте причину: недостаточная роль, превышение лимита, истёкшее подтверждение, изменение заказа или ошибка Shopify.

Аудит должен позволять связать четыре события: исходный запрос, предпросмотр, подтверждение и выполнение. Полезно также хранить версию политики разрешений и версию MCP-сервера.

Проверка результата

Перед включением права на возвраты выполните проверку в тестовом или изолированном контуре, если он предусмотрен вашей инфраструктурой. Не считайте успешным результатом ответ модели — проверяйте фактические записи сервера и Shopify.

  1. Пользователь только с orders.read видит заказ, но получает отказ на подготовку возврата.
  2. Пользователь с refunds.prepare получает предпросмотр, но не может выполнить возврат.
  3. Выполнение без confirmation ID отклоняется.
  4. Изменение суммы после подтверждения отклоняется.
  5. Повторное использование confirmation ID отклоняется.
  6. Превышение лимита суммы отклоняется до вызова Shopify.
  7. Запрос к другому магазину отклоняется.
  8. Каждая попытка появляется в аудите без секретов.
  9. Повторная доставка одного request ID не создаёт второй возврат.

Для безопасной проверки конфигурации можно использовать команду, которая завершится ошибкой при обнаружении опасной комбинации:

mcp-server policy check \
  --config ./mcp-shopify.json \
  --deny-unconfirmed-writes \
  --deny-wildcard-tools \
  --deny-admin-token-in-logs

Это также пример интерфейса. Если у вашего сервера нет такой проверки, реализуйте эквивалентную проверку в CI или отдельном валидаторе конфигурации.

Типовые ошибки

«Мы запретили возврат в системном промпте»

Инструкции модели не заменяют авторизацию. Модель может ошибиться, получить конфликтующие инструкции или вызвать инструмент в неожиданном контексте. Ограничение должно быть на сервере.

«У сотрудника есть доступ к Shopify, значит, можно передать его токен»

Персональный токен расширяет поверхность атаки и усложняет отзыв доступа. Используйте отдельные серверные credentials и связывайте операции с проверенной идентичностью сотрудника.

«Достаточно кнопки “ОК”»

Подтверждение без снимка параметров не защищает от подмены заказа или суммы между предпросмотром и выполнением. Подтверждайте подписанный или хешированный набор параметров.

«Сделаем один универсальный инструмент»

Универсальный прокси скрывает реальные границы доступа. Явные инструменты проще проверять, логировать и отзывать по отдельности.

«Аудит добавим после запуска»

Без аудита невозможно надёжно установить, кто инициировал возврат, какие параметры видел сотрудник и почему сервер разрешил операцию. Журнал должен быть частью первой версии.

Ограничения схемы

Эта модель не решает автоматически вопросы бизнес-политики: сроки возврата, исключения для отдельных товаров, налоговый учёт, спорные платежи и требования конкретного магазина нужно формализовать отдельно. Она также не делает внешнюю систему транзакционной: состояние заказа может измениться между чтением и выполнением, поэтому сервер обязан повторять критические проверки непосредственно перед вызовом Shopify.

Если MCP-сервер обслуживает несколько магазинов или несколько команд, добавьте изоляцию tenant-контекста и отдельные ключи идемпотентности. Не полагайтесь на то, что модель правильно выберет магазин из текста диалога.

Итоговая схема

Безопасная архитектура выглядит так: ассистент ищет заказ через инструмент чтения, сервер проверяет область доступа, отдельный инструмент строит предпросмотр возврата, сотрудник подтверждает конкретные параметры, а сервер повторно проверяет роль, лимиты и актуальное состояние перед выполнением. Каждое решение фиксируется в аудите.

Так MCP-сервер остаётся узким шлюзом с понятными полномочиями, а не скрытым административным клиентом Shopify. Дополнительные практические материалы собраны в разделе guides, а термины — в глоссарии.
