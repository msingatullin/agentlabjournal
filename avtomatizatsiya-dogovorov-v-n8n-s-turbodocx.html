Как автоматизировать договоры в n8n с TurboDocx

Разберём сценарий, в котором данные о контрагенте превращаются в договор из шаблона, проходят согласование в Slack, отправляются на электронную подпись, а готовый PDF автоматически попадает в SharePoint.

В статье используется workflow — последовательность связанных шагов автоматизации. Его можно собрать в n8n из стандартных узлов и одного HTTP-запроса к API TurboDocx. Названия полей и адреса API ниже показаны как пример: перед запуском сверяйте их с актуальной документацией ваших сервисов.

Что получится в итоге

Сценарий будет запускаться после появления заявки на договор и выполнять такой маршрут:

  1. получает данные сделки и контрагента;
  2. проверяет обязательные поля;
  3. создаёт документ из шаблона TurboDocx;
  4. отправляет ссылку на согласование в Slack;
  5. после одобрения отправляет договор на подпись;
  6. периодически проверяет статус подписания;
  7. скачивает подписанный PDF и сохраняет его в SharePoint.
Важно. Электронная подпись и юридическая значимость документа зависят от выбранного сервиса, типа подписи и требований вашей юрисдикции. Этот пример описывает техническую автоматизацию, а не юридическую консультацию.

Перед началом

Подготовьте:

  • рабочий экземпляр n8n;
  • шаблон договора в TurboDocx с понятными переменными;
  • учётные данные TurboDocx API;
  • Slack-приложение или webhook для уведомлений;
  • доступ к SharePoint и папку назначения;
  • источник заявок: форма, CRM, таблица или webhook.

Не вставляйте токены в узлы, JSON-файлы или сообщения Slack. Храните их в Credentials n8n или в защищённых переменных окружения. Для тестов используйте отдельные тестовые учётные записи и папку, чтобы не смешивать черновики с рабочими договорами.

Шаг 1. Определите структуру данных

Сначала договоритесь о едином формате заявки. Например, входной webhook может передавать такие поля: 

{
  "contractNumber": "DEMO-001",
  "companyName": "ООО «Пример»",
  "companyInn": "0000000000",
  "signerName": "Иван Иванов",
  "signerEmail": "signer@example.com",
  "amount": 100000,
  "currency": "RUB",
  "contractDate": "2026-11-10",
  "templateId": "your-template-id"
}

Это демонстрационный payload, а не готовые реальные реквизиты. В вашем процессе добавьте только те поля, которые нужны шаблону и сервису подписи. Поля, влияющие на юридический текст, лучше не формировать свободным текстом в Slack.

Шаг 2. Создайте начало workflow в n8n

  1. Добавьте узел Webhook с методом POST.
  2. Скопируйте тестовый URL и отправьте на него демонстрационный payload.
  3. Добавьте узел Set или Edit Fields для нормализации имён.
  4. Добавьте узел IF, который проверит номер договора, email, шаблон и сумму.

Если обязательного поля нет, завершайте ветку понятным сообщением об ошибке. Не отправляйте неполную заявку в TurboDocx: иначе ошибка появится позже, когда документ уже создан или отправлен на подпись.

Шаг 3. Сгенерируйте договор из шаблона TurboDocx

Используйте узел HTTP Request. В нём укажите метод, URL и формат тела запроса согласно документации вашей версии TurboDocx. Обычно в запрос передают идентификатор шаблона и словарь значений для переменных. 

{
  "templateId": "={{ $json.templateId }}",
  "variables": {
    "contractNumber": "={{ $json.contractNumber }}",
    "companyName": "={{ $json.companyName }}",
    "companyInn": "={{ $json.companyInn }}",
    "signerName": "={{ $json.signerName }}",
    "signerEmail": "={{ $json.signerEmail }}",
    "amount": "={{ $json.amount }}",
    "currency": "={{ $json.currency }}",
    "contractDate": "={{ $json.contractDate }}"
  }
}

Сохраните из ответа минимум идентификатор документа, ссылку на предпросмотр и текущий статус. Названия полей ответа могут отличаться, поэтому один раз выполните запрос вручную и сопоставьте фактический JSON с выражениями n8n.

После HTTP Request удобно поставить узел Set с внутренними полями: documentId, previewUrl, contractNumber и approvalStatus. Так последующие узлы не зависят от структуры всего ответа API.

Шаг 4. Организуйте согласование в Slack

Добавьте узел Slack или HTTP Request к вашему Slack webhook. Сообщение должно содержать номер договора, контрагента, сумму, ссылку на предпросмотр и понятный способ принять решение. 

Нужна проверка договора {{ $json.contractNumber }}

Контрагент: {{ $json.companyName }}
Сумма: {{ $json.amount }} {{ $json.currency }}
Документ: {{ $json.previewUrl }}

Ответьте в выделенном канале:
APPROVE — согласовать
REJECT — вернуть на доработку

Для простого сценария можно использовать ответ в канале и узел, который разбирает текст. Для более надёжного варианта используйте интерактивные кнопки Slack с callback URL: так вы избежите случайного срабатывания на обычное сообщение.

После Slack добавьте Wait или отдельный webhook для получения решения. Затем узел Switch разделит поток на две ветки: APPROVE продолжает подписание, а REJECT записывает причину и уведомляет инициатора.

Шаг 5. Отправьте документ на электронную подпись

На ветке согласования вызовите операцию TurboDocx, которая создаёт пакет или запрос на подписание. В запросе укажите идентификатор документа и данные подписанта из проверенной заявки. 

{
  "documentId": "={{ $json.documentId }}",
  "signers": [
    {
      "name": "={{ $json.signerName }}",
      "email": "={{ $json.signerEmail }}"
    }
  ]
}

Сохраните идентификатор операции подписи, например signatureRequestId. Не считайте документ подписанным только потому, что API вернул успешный ответ на создание запроса: это означает лишь, что запрос принят.

Шаг 6. Отслеживайте статус

Есть два рабочих подхода.

Webhook от сервиса

Если TurboDocx поддерживает уведомления, создайте отдельный узел Webhook для событий подписи. Проверьте подпись входящего запроса, найдите договор по signatureRequestId и продолжите обработку только для финального статуса.

Периодическая проверка

Если webhook недоступен, используйте связку Wait → HTTP Request → IF. Запрашивайте статус по идентификатору операции, проверяйте значение и повторяйте цикл через разумный интервал. Обязательно добавьте счётчик попыток и конечный статус timeout, чтобы workflow не выполнялся бесконечно. 

pending  → подождать и проверить снова
signed   → скачать PDF и сохранить
rejected → уведомить инициатора
expired  → запросить новое подписание
timeout  → передать в ручную обработку

Шаг 7. Сохраните подписанный PDF в SharePoint

После статуса signed получите файл через API TurboDocx. В n8n убедитесь, что ответ обрабатывается как бинарные данные, а не как текстовый JSON.

  1. Добавьте HTTP Request для скачивания подписанного файла.
  2. Укажите режим ответа File или эквивалентный бинарный режим.
  3. Назовите бинарное свойство, например data.
  4. Добавьте узел SharePoint для загрузки файла в нужную библиотеку.
  5. Сформируйте имя вроде DEMO-001-signed.pdf.

Папку назначения лучше задавать через конфигурацию или отдельный узел, а не дублировать в нескольких выражениях. Перед загрузкой нормализуйте имя файла и не включайте в него персональные данные, если они не нужны для поиска.

Рекомендуемая схема узлов

Webhook
  → Edit Fields
  → IF: обязательные поля
  → HTTP Request: TurboDocx, создать документ
  → Slack: запросить согласование
  → Wait/Webhook: получить решение
  → Switch: APPROVE или REJECT
      APPROVE
        → HTTP Request: создать подпись
        → Wait/Webhook: статус
        → IF: signed
        → HTTP Request: скачать PDF
        → SharePoint: загрузить файл
        → Slack: завершено
      REJECT
        → Slack: вернуть на доработку

Проверка результата

Проверяйте сценарий по этапам, используя тестовые данные:

  • заявка с заполненными полями создаёт документ из правильного шаблона;
  • пустой email останавливает поток до вызова TurboDocx;
  • сообщение в Slack содержит корректную ссылку;
  • REJECT не запускает подписание;
  • повторная проверка статуса не создаёт второй запрос на подпись;
  • подписанный файл имеет PDF-расширение и непустой размер;
  • SharePoint сохраняет файл в ожидаемой папке;
  • ошибка на любом шаге оставляет запись, по которой можно найти договор.

В n8n откройте выполнение workflow и проверьте входные и выходные данные каждого узла. Секреты в логах не выводите: если API возвращает заголовки или токены, удаляйте их из промежуточных данных перед передачей дальше.

Безопасные команды для локальной проверки webhook

Ниже — безопасный пример с тестовыми значениями. Не подставляйте в команду реальные персональные данные или токены. 

curl -X POST "https://n8n.example.test/webhook/contract-demo" \
  -H "Content-Type: application/json" \
  --data @payload.json

Файл payload.json создайте локально из демонстрационного примера выше. В рабочей среде используйте HTTPS, ограничивайте доступ к webhook и добавляйте проверку подписи запроса или секретного заголовка, если это поддерживает ваш источник данных.

Типовые ошибки

Переменные не подставляются

Проверьте точное написание переменной в шаблоне и JSON. companyName и company_name — разные ключи. Для отладки временно передайте в шаблон тестовое значение и сравните результат с входным JSON.

Slack сообщает об успехе, но workflow не продолжает работу

Отправка сообщения и получение ответа — разные события. Проверьте callback URL, настройки Slack-приложения и способ возврата события в ожидаемое выполнение n8n.

PDF сохраняется пустым

Убедитесь, что узел скачивания получает финальный статус и работает в бинарном режиме. Также проверьте, что в SharePoint передаётся именно бинарное свойство, а не URL или строковое представление ответа.

Создаются дубликаты запросов на подпись

Добавьте идемпотентность: перед созданием нового запроса ищите сохранённый signatureRequestId. Повторный запуск должен продолжать существующую операцию или завершаться без повторной отправки.

Ограничения сценария

Конкретные названия операций TurboDocx, форматы статусов, требования к подписантам и параметры SharePoint зависят от подключённых сервисов и их текущих API. Поэтому выражения в примере — каркас, который нужно сопоставить с вашей конфигурацией.

Не переносите в Slack полный текст договора, если для согласования достаточно ссылки. Ограничьте права n8n, TurboDocx и SharePoint принципом минимально необходимого доступа. Добавьте ручную очередь для спорных случаев, просроченных подписаний и ошибок, которые нельзя безопасно повторить автоматически.

Итог

Теперь у вас есть воспроизводимая основа для автоматизации: n8n принимает заявку, TurboDocx создаёт документ, Slack фиксирует решение, сервис подписи возвращает финальный статус, а SharePoint становится единым местом хранения подписанного PDF.

Для следующего шага настройте отдельную таблицу или базу с идентификаторами заявки, документа и операции подписи. Это упростит повторные запуски, аудит и ручную обработку исключений.
