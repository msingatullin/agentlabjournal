Практика До 12 минут Уровень: продвинутый

Инварианты должны защищать состояние, а не отдельную функцию

Если бизнес-правило важно для данных, оно не должно жить только внутри одной функции. Иначе вторая точка записи — например, PUT вместо POST — постепенно станет обходом ограничения. Надёжная граница находится перед сохранением: приложение сначала вычисляет итоговое состояние, затем проверяет его и только после этого записывает.

В этой статье инвариант — это условие, которое должно оставаться истинным для допустимого состояния системы. Например: у одной категории не может быть двух опубликованных статей с одинаковым каноническим адресом.

Проблема: правило привязано к маршруту

Представим ресурс статьи. Новая статья создаётся через POST /articles, а существующая редактируется через PUT /articles/{id}. Требование одинаковое для обоих сценариев:

В состоянии published комбинация section + slug должна быть уникальной.

Наивная реализация часто выглядит так: проверка добавляется в обработчик POST, потому что именно там впервые появляется статья. PUT при этом обновляет поля напрямую и проверку не повторяет. Ошибка проявляется позже: редактор меняет черновик на опубликованный или меняет slug уже опубликованной статьи, и ограничение обходится без единой строки в POST-коде. 

POST /articles
  ├─ проверить входные данные
  ├─ проверить уникальность
  └─ вставить запись

PUT /articles/{id}
  ├─ прочитать статью
  ├─ применить изменения
  └─ обновить запись

У этих маршрутов разные входы, но одна и та же ответственность: они переводят хранилище из старого состояния в новое. Поэтому инвариант должен проверяться на переходе состояния, а не в конкретном HTTP-методе.

Сначала вычислите итоговое состояние

Для POST итоговое состояние строится из тела запроса и значений по умолчанию. Для PUT — из текущей записи и частичного набора изменений. В обоих случаях проверке нужно передать один и тот же объект, уже нормализованный и готовый к записи. 

function buildFinalArticle(input, currentArticle = null) {
  const finalArticle = {
    ...currentArticle,
    ...input
  };

  return {
    ...finalArticle,
    slug: normalizeSlug(finalArticle.slug),
    section: normalizeSection(finalArticle.section),
    status: normalizeStatus(finalArticle.status)
  };
}

Важно не проверять только поля из запроса. Если PUT не содержит status, итоговое значение должно прийти из текущей записи. Иначе guard увидит неполную картину и может принять запрещённый переход.

Один guard для всех точек записи

Guard получает итоговое состояние и контекст операции. Он не должен знать, пришли данные через POST, PUT, импорт или административную команду. 

async function assertArticleStateAllowed(finalArticle, context) {
  if (finalArticle.status !== "published") {
    return;
  }

  const duplicate = await articleRepository.findPublishedBySectionAndSlug({
    section: finalArticle.section,
    slug: finalArticle.slug,
    excludeId: context.articleId ?? null
  });

  if (duplicate) {
    throw new ConflictError(
      "Опубликованная статья с таким section и slug уже существует"
    );
  }
}

Параметр excludeId нужен для PUT. При обновлении статьи сама текущая запись не должна считаться дубликатом. Для POST он равен null, потому что исключать ещё нечего.

Как подключить guard к POST и PUT

Маршруты могут оставаться разными, но последовательность действий должна быть одинаковой: получить текущие данные, собрать итоговое состояние, вызвать guard, выполнить запись. 

async function createArticle(request) {
  const finalArticle = buildFinalArticle(request.body);

  await assertArticleStateAllowed(finalArticle, {
    operation: "create"
  });

  return articleRepository.insert(finalArticle);
}

async function updateArticle(request) {
  const currentArticle =
    await articleRepository.findById(request.params.id);

  if (!currentArticle) {
    throw new NotFoundError("Статья не найдена");
  }

  const finalArticle = buildFinalArticle(
    request.body,
    currentArticle
  );

  await assertArticleStateAllowed(finalArticle, {
    operation: "update",
    articleId: currentArticle.id
  });

  return articleRepository.update(
    currentArticle.id,
    finalArticle
  );
}

Теперь одинаковое правило применяется к двум сценариям. Если статья остаётся черновиком, проверка публикационного конфликта не нужна. Если PUT переводит её из черновика в опубликованное состояние, итоговый объект попадёт в тот же guard, что и новый объект из POST.

Почему проверки приложения недостаточно

Проверка перед записью устраняет дублирование логики, но не заменяет ограничение на уровне базы данных. Две параллельные операции могут одновременно выполнить поиск, обе не найти дубликат и затем обе попытаться записать строку.

Поэтому правило лучше защищать в два слоя:

  1. общий guard в приложении даёт понятную ошибку и учитывает бизнес-условия;
  2. уникальное ограничение в базе данных закрывает окно гонки между проверкой и записью.

Если база данных поддерживает частичный уникальный индекс, концептуальная форма ограничения может выглядеть так: 

CREATE UNIQUE INDEX articles_published_section_slug_idx
ON articles (section, slug)
WHERE status = 'published';

Это пример SQL-схемы. Точный синтаксис и возможности зависят от используемой СУБД. Если частичные индексы недоступны, аналогичное правило можно выразить отдельным ключом публикации, вычисляемым полем или другой конструкцией, принятой в конкретной базе.

Воспроизводимые шаги

Ниже — безопасный локальный сценарий проверки. Команды не удаляют данные и используют только HTTP-запросы к локальному экземпляру приложения. Замените порт и идентификаторы на значения своего проекта. 

# 1. Создать опубликованную статью
curl --fail-with-body -X POST http://localhost:3000/articles \
  -H 'Content-Type: application/json' \
  --data '{"section":"agents","slug":"state-guards","status":"published","title":"Первая статья"}'

# 2. Попробовать создать дубликат
curl --fail-with-body -X POST http://localhost:3000/articles \
  -H 'Content-Type: application/json' \
  --data '{"section":"agents","slug":"state-guards","status":"published","title":"Дубликат"}'

# 3. Создать черновик с тем же ключом
curl --fail-with-body -X POST http://localhost:3000/articles \
  -H 'Content-Type: application/json' \
  --data '{"section":"agents","slug":"state-guards","status":"draft","title":"Черновик"}'

# 4. Перевести черновик в published
curl --fail-with-body -X PUT http://localhost:3000/articles/DRAFT_ID \
  -H 'Content-Type: application/json' \
  --data '{"status":"published"}'

Ожидаемый результат для примера: первый POST проходит, второй получает конфликт, черновик создаётся, а PUT, переводящий его в published, получает тот же конфликт. Если у приложения другой формат ошибок, проверяйте не текст, а HTTP-статус и отсутствие запрещённой записи.

Проверка результата

Проверка должна подтверждать не только ответ API, но и состояние хранилища. После сценария убедитесь, что:

  • в базе существует не более одной опубликованной статьи с данной парой ключей;
  • неудачный POST не создал запись;
  • неудачный PUT не изменил черновик на опубликованный;
  • обновление опубликованной статьи без изменения уникального ключа не конфликтует с самой собой;
  • ошибка от ограничения базы преобразуется в предсказуемый ответ API.

Для проверки гонки запустите два одинаковых запроса только в тестовой или локальной среде, где разрешено создавать временные данные. Один запрос должен завершиться успешно, а второй — получить конфликт на уровне приложения или базы данных. Не используйте для такой проверки продуктивные записи.

Типовые ошибки

Проверяется только тело запроса

PUT часто является частичным обновлением. Если guard получает только присланные поля, он не знает текущий статус, slug или раздел. Исправление — сначала собрать полный итоговый объект.

POST и PUT вызывают разные проверки

Два почти одинаковых правила неизбежно расходятся. Оставьте в маршрутах только сбор контекста и вызов общей проверки.

Нормализация выполняется после проверки

Значения State-Guards и state-guards могут стать одинаковыми после нормализации. Проверяйте именно нормализованное итоговое состояние, иначе guard защищает не тот ключ, который будет записан.

Учитывается только ошибка приложения

Проверка чтением не атомарна с последующей записью. Ограничение базы данных обязательно, если инвариант должен выдерживать конкурентные запросы.

Guard изменяет данные

Проверка должна быть предсказуемой и по возможности не иметь побочных эффектов. Если она сама создаёт записи или меняет статус, становится сложнее понять, какой именно переход был разрешён.

Ограничения подхода

Общий guard не решает автоматически проблемы старых некорректных данных. Если дубликаты уже существуют, сначала потребуется отдельная процедура инвентаризации и исправления. Не следует включать жёсткое ограничение базы, не понимая, как обрабатываются существующие нарушения.

Кроме того, одного guard может быть недостаточно для правил, зависящих от нескольких агрегатов, временных интервалов или внешних систем. В таких случаях нужны транзакции, блокировки, согласованная модель конкуренции или отдельный процесс подтверждения. Сам принцип остаётся тем же: проверять состояние, которое реально будет записано.

Итог

Инварианты должны защищать состояние, а не отдельную функцию. POST и PUT могут отличаться форматом входа, авторизацией и способом поиска текущей записи, но перед сохранением они должны проходить через одну и ту же модель: итоговое состояние → общий guard → атомарная запись с ограничением хранилища.
