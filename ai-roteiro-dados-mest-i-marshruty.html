AI-маршруты без выдуманных данных: разделяем предложения, места и маршруты

Туристический помощник может звучать убедительно и при этом незаметно смешивать предположение модели с фактами о местах, расписаниями и результатами расчёта поездки. Надёжный прототип строится вокруг границ ответственности: модель интерпретирует намерение, поиск возвращает кандидатов, картографический сервис считает маршрут, а пользователь подтверждает действия.

Почему один ответ модели недостаточен

Запрос «составь маршрут по Казани на два дня, добавь татарскую кухню и не делай дни слишком насыщенными» содержит предпочтения, ограничения и неявные допущения. Но в нём нет достоверного списка заведений, текущих часов работы, координат или времени в пути. Если отдать весь запрос одной модели, она может оформить правдоподобный рассказ как готовый план поездки.

Проблема не в самой генерации. Проблема возникает, когда разные типы утверждений получают одинаковый статус доверия. В прототипе полезно заранее разделить четыре слоя:

  1. Предложение — гипотеза о том, что может подойти пользователю.
  2. Место — объект, найденный во внешнем источнике с идентификатором и координатами.
  3. Маршрут — результат вычисления между подтверждёнными точками.
  4. Действие — операция, которую система выполнит только после согласия пользователя.

Целевая схема прототипа

Удобная минимальная цепочка выглядит так: 

запрос пользователя
        ↓
1. интерпретация намерения
        ↓
2. поиск и нормализация мест
        ↓
3. проверка ограничений
        ↓
4. расчёт маршрутов
        ↓
5. сборка ответа
        ↓
6. подтверждение действий

Ключевой принцип: каждый следующий этап получает структурированный результат предыдущего этапа, а не свободный текст. Свободный текст можно показать человеку, но не следует использовать как единственный источник данных для следующего вызова.

Шаг 1. Интерпретируйте запрос без поиска мест

На первом этапе модель должна извлечь намерение и ограничения. Она не должна утверждать, что конкретное кафе существует, открыто или находится рядом.

Пример входной структуры:

{
  "destination": "Казань",
  "dates": {
    "start": "2026-06-12",
    "end": "2026-06-14"
  },
  "interests": ["татарская кухня", "история", "прогулки"],
  "pace": "умеренный",
  "transport": ["пешком", "общественный транспорт"],
  "constraints": {
    "max_daily_stops": 4,
    "avoid_long_transfers": true
  },
  "missing": ["точка старта", "бюджет"]
}

Поле missing важно не меньше остальных. Если точка старта влияет на расчёт, система должна запросить её или явно использовать согласованное значение по умолчанию. Нельзя молча превращать неопределённость в факт.

Граница промпта

Для интерпретатора задайте отрицательное правило: «Не перечисляй конкретные места, если они не переданы во входных данных. Не сообщай часы работы, цены, расстояния и наличие бронирования. Возвращай только структуру намерения и список неясностей». Это не заменяет проверку схемы, но уменьшает риск ложных деталей.

Шаг 2. Ищите места как данные, а не как продолжение текста

Поисковый слой получает понятные запросы: категория, город, район, язык или иное ограничение. Его результат нужно нормализовать в записи с устойчивым идентификатором, названием, координатами и ссылкой на источник. 

{
  "place_id": "provider-specific-id",
  "name": "Название объекта",
  "category": "restaurant",
  "coordinates": {
    "lat": 55.000000,
    "lon": 49.000000
  },
  "address": "Адрес из источника",
  "source": {
    "provider": "search-provider",
    "retrieved_at": "2026-06-01T10:00:00Z"
  },
  "verification": {
    "coordinates": "verified",
    "opening_hours": "unknown"
  }
}

Значение provider-specific-id в этом фрагменте — обозначение формата, а не настоящий идентификатор. В рабочей системе его заменяет значение, полученное от подключённого поставщика данных.

Не просите модель «найти хорошие места» и не принимайте её список без последующего поиска. Модель может сформулировать критерии ранжирования, но кандидаты должны появиться из отдельного источника.

Шаг 3. Отделите факт от оценки

Полезно хранить отдельно поля, пришедшие от провайдера, и поля, вычисленные системой. Например, адрес и координаты — данные места; «подходит для спокойного вечера» — оценка по пользовательскому запросу; «тридцать минут пешком» — результат расчёта маршрута на конкретный момент и с конкретным режимом передвижения.

Слой Что допустимо Что недопустимо без проверки
Предложение «Можно рассмотреть места с татарской кухней» «Это место точно открыто в понедельник»
Место Название, координаты, источник Скрытое заполнение отсутствующих полей
Маршрут Время, расстояние, режим, дата расчёта Расстояние, посчитанное «на глаз»
Действие Запрос подтверждения перед бронированием или экспортом Непрозрачный вызов внешнего API

Шаг 4. Рассчитывайте маршрут только по подтверждённым точкам

Маршрутизатор не должен получать названия из ответа модели. Передавайте ему идентификаторы или координаты, которые прошли нормализацию. Результат сохраняйте вместе с режимом передвижения, временем расчёта и статусом точности. 

{
  "route": {
    "origin": "user-confirmed-origin",
    "stops": [
      "verified-place-1",
      "verified-place-2"
    ],
    "mode": "walking"
  },
  "result": {
    "distance_m": 3200,
    "duration_s": 2400,
    "calculated_at": "2026-06-01T10:05:00Z",
    "status": "calculated"
  }
}

Если сервис не вернул маршрут, это должно быть явным состоянием unavailable или needs_review, а не поводом подставить приблизительное число. Можно предложить альтернативу, но пометить её как предложение, требующее нового расчёта.

Шаг 5. Собирайте ответ с видимыми границами

Финальный текст может быть дружелюбным, но его происхождение должно оставаться понятным. Для каждого пункта удобно показывать короткие метки: «найдено», «рассчитано», «предложено» или «нужно проверить».

Пример безопасной формулировки: «Я нашёл два объекта по заданным критериям. Время перехода между ними рассчитано для пешего режима. Часы работы не подтверждены, поэтому проверьте их перед поездкой». Такая фраза не скрывает пробелы и не превращает неполные данные в рекомендацию с ложной уверенностью.

Ранжирование тоже должно быть объяснимым. Сначала применяйте жёсткие ограничения: город, дата, доступность координат, допустимый режим. Затем используйте мягкие предпочтения: интересы, темп и разнообразие остановок. Если оценка построена моделью, храните её как оценку, а не как свойство места.

Шаг 6. Подтверждайте действия пользователя

Просмотр маршрута и внешнее действие — разные операции. К внешнему действию относятся бронирование, отправка приглашения, экспорт в календарь, заказ транспорта или передача контактных данных.

Перед действием покажите пользователю сводку: что произойдёт, какие данные будут переданы, какой объект выбран и можно ли отменить операцию. На уровне сервера добавьте проверку, что подтверждение относится именно к текущей версии плана. 

{
  "plan_version": "v3",
  "action": "export_calendar",
  "items": ["verified-place-1", "verified-place-2"],
  "user_confirmation": {
    "confirmed": true,
    "confirmed_at": "2026-06-01T10:10:00Z"
  }
}

Если план изменился после подтверждения, старое подтверждение нельзя автоматически переиспользовать. Пользователь должен увидеть новую версию и подтвердить её заново.

Воспроизводимая локальная проверка

Ниже приведён безопасный минимальный набор команд для проверки структуры страницы. Команды только читают файлы и не требуют секретов, сетевых ключей или публикации. 

rg --files
rg -n 'site-header|reading|site-footer|canonical|application/ld\+json' \
  ai-roteiro-dados-mest-i-marshruty.html
python -m html.parser ai-roteiro-dados-mest-i-marshruty.html

Если в проекте нет локального валидатора, проверьте вручную: подключены ли style.css и reading.css, совпадает ли canonical с URL статьи, а обязательные элементы находятся в нужном порядке.

Для проверки логики прототипа используйте фикстуры с явно вымышленными идентификаторами и пометкой example. Не подменяйте ими реальные результаты поиска и не называйте их фактами в интерфейсе.

Критерии готовности прототипа

  • Интерпретатор возвращает структуру намерения и отмечает неясности.
  • Места приходят из отдельного источника и имеют идентификатор происхождения.
  • Отсутствующие поля не заполняются догадкой без явной пометки.
  • Расчёт маршрута выполняется только по подтверждённым точкам.
  • Недоступный расчёт отображается как ошибка или состояние проверки.
  • В ответе различаются предложения, факты о местах и результаты маршрутизации.
  • Внешние действия требуют актуального подтверждения пользователя.
  • Логи позволяют восстановить, какая версия плана и какие данные использовались.

Типовые ошибки

«Модель уже назвала место — значит, оно существует»

Название из генерации — поисковый запрос или гипотеза. До получения записи от провайдера оно не должно попадать в маршрут и не должно отображаться как проверенная рекомендация.

«Координаты можно получить из названия самостоятельно»

Геокодирование — отдельный вызов с собственными ошибками неоднозначности. Сохраняйте исходную строку, результат геокодирования и уровень совпадения.

«Если маршрут не рассчитался, можно показать примерное время»

Приблизительное время может быть полезным только как явно обозначенная оценка, а не как результат маршрутизатора. Для планирования поездки безопаснее показать отсутствие расчёта и запросить уточнение.

«Подтверждение можно считать постоянным»

Любое изменение места, даты, порядка остановок или параметров действия должно инвалидировать старое подтверждение.

Ограничения и следующий шаг

Такая архитектура не устраняет устаревание внешних данных: часы работы, расписания, перекрытия и доступность могут измениться после поиска. Она также не гарантирует, что провайдер одинаково хорошо распознает все названия и адреса. Поэтому в интерфейсе нужны дата получения данных, источник и понятное состояние «нужно проверить».

Для следующей итерации добавьте трассировку по этапам: входной запрос, интерпретацию, найденные идентификаторы, параметры маршрутизатора, версию плана и подтверждение. Это позволит отличить ошибку поиска от ошибки генерации и не расследовать весь разговор как одну неделимую строку.

Дополнительные практические материалы собраны в разделе guides, а термины и границы ответственности — в глоссарии.

Итог: модель может предложить структуру путешествия, но не должна незаметно становиться источником фактов. Раздельные этапы, происхождение данных, явные состояния ошибки и подтверждение действий превращают туристический ответ в проверяемый прототип.
