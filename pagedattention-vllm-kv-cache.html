KV-кэш LLM под нагрузкой: проверяем PagedAttention и vLLM

Уровень: продвинутый Время чтения: до 12 минут Практика: запуск сервера и нагрузочное сравнение

При обслуживании нескольких пользователей GPU может упереться не в вычислительные блоки, а в память, занятую KV-кэшем. Проблема усугубляется фрагментацией: последовательности имеют разную длину, запросы завершаются в разное время, а зарезервированные участки памяти не всегда удаётся использовать повторно. В этом материале разберём, как запустить vLLM и построить сравнение, в котором видны пропускная способность, задержка первого токена, межтокенная задержка и вытеснение запросов.

Что именно проверяем

PagedAttention организует KV-кэш блоками фиксированного размера. Логическая последовательность может занимать несколько блоков, а физические блоки не обязаны лежать подряд. Это снижает требования к непрерывной области памяти и упрощает совместное использование KV-кэша несколькими активными последовательностями.

Важно отделять механизм управления памятью от общей производительности сервера. На итог влияют модель, точность, длина контекста, размер батча, параметры планировщика, версия vLLM, драйвер и конкретный GPU. Поэтому сравнение ниже — это методика измерения для вашей конфигурации, а не заранее заявленный результат.

Перед стартом

Нужны:

  • NVIDIA GPU с рабочим драйвером и достаточным объёмом видеопамяти;
  • Docker с доступом к NVIDIA Container Toolkit либо рабочее Python-окружение;
  • локально доступные веса модели, которую разрешено запускать в вашей среде;
  • одинаковые модель и параметры для всех сравниваемых прогонов.

Не публикуйте токены доступа в командной строке, логах CI или HTML-отчётах. Если модель требует авторизации, передайте секрет через менеджер секретов или переменную окружения, не добавляя её значение в скрипт и историю команд.

Запуск vLLM

Ниже приведён шаблон команды. Значение MODEL_ID замените на разрешённый идентификатор модели или путь к локальным весам. Параметры оставлены явными, чтобы их можно было зафиксировать в отчёте. 

MODEL_ID="your-model-id"

docker run --rm --gpus all \
  -p 8000:8000 \
  -v "$PWD/models:/models:ro" \
  vllm/vllm-openai:latest \
  --model "$MODEL_ID" \
  --host 0.0.0.0 \
  --port 8000 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 4096

Для воспроизводимости зафиксируйте тег образа вместо latest, а также запишите модель, версию CUDA, драйвер, тип GPU и значения всех флагов. Если модель загружается из локального каталога, монтируйте его только для чтения, как в примере.

Проверка результата

Сначала убедитесь, что сервер отвечает и сообщает ожидаемую модель:

curl --fail --silent http://127.0.0.1:8000/v1/models

Затем выполните один короткий запрос без нагрузки:

curl --fail --silent http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "your-model-id",
    "messages": [
      {"role": "user", "content": "Ответь одним предложением: что проверяет этот стенд?"}
    ],
    "max_tokens": 32,
    "temperature": 0
  }'

Проверка считается успешной, если эндпоинт /v1/models возвращает ожидаемую модель, запрос завершаетcя кодом HTTP 200, а в логах сервера нет ошибки загрузки CUDA, нехватки памяти или несовместимости архитектуры.

План нагрузочного эксперимента

Один прогон должен измерять не только среднее время ответа. Зафиксируйте четыре группы метрик:

  1. Пропускная способность — завершённые токены в секунду и завершённые запросы в секунду.
  2. TTFT — время от отправки запроса до получения первого токена.
  3. Межтокенная задержка — интервалы между последующими токенами, включая p50 и p95.
  4. Вытеснение — число запросов, которые были прерваны, вытеснены или повторно поставлены планировщиком.

Используйте несколько уровней конкурентности, например 1, 2, 4, 8 и далее до момента, когда сервер начинает заметно накапливать очередь или возвращать ошибки. Сам набор уровней — параметр эксперимента: его следует выбрать под ваш GPU и явно записать.

Для каждого уровня отправляйте одинаковые запросы: одинаковое число входных токенов, одинаковый max_tokens, одинаковую температуру и одинаковую схему распределения длин. Сначала выполните прогревочный прогон, затем собирайте результаты нескольких повторов. Прогрев не включайте в статистику.

Минимальный клиент для потоковых ответов

Клиент должен фиксировать монотонные временные метки: момент отправки, момент первого полученного токена и момент каждого следующего фрагмента. Ниже — безопасный каркас для одного запроса; он не является результатом измерения и не заменяет генератор конкурентной нагрузки. 

python -m pip install --upgrade openai

python - <<'PY'
import os
import time
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",
    api_key=os.environ.get("VLLM_API_KEY", "local-only")
)

started = time.perf_counter()
first = None
chunks = 0

stream = client.chat.completions.create(
    model="your-model-id",
    messages=[{"role": "user", "content": "Сформулируй короткий технический ответ."}],
    max_tokens=128,
    temperature=0,
    stream=True,
)

for event in stream:
    text = event.choices[0].delta.content or ""
    if text:
        now = time.perf_counter()
        if first is None:
            first = now
        chunks += 1

finished = time.perf_counter()
print({
    "ttft_ms": None if first is None else round((first - started) * 1000, 2),
    "stream_duration_ms": round((finished - started) * 1000, 2),
    "received_chunks": chunks
})
PY

Для полноценного стенда добавьте идентификатор запроса, число реально полученных токенов, ограничение таймаута, обработку HTTP-ошибок и конкурентный запуск. Не смешивайте результаты запросов с разными длинами контекста в одну среднюю без разбиения по группам.

Как сравнивать режимы

Сравнивать следует конфигурации, у которых меняется только один фактор. Например, можно менять доступный бюджет видеопамяти через --gpu-memory-utilization или ограничение длины контекста, но нельзя одновременно менять модель, точность и уровень конкурентности.

Для каждой точки сохраните:

  • конкурентность и длительность прогона;
  • распределение входных и выходных токенов;
  • среднее, p50 и p95 для TTFT;
  • среднее, p50 и p95 межтокенной задержки;
  • агрегированную скорость генерации;
  • число ошибок, таймаутов и вытеснений;
  • пиковое потребление видеопамяти и сообщения планировщика из логов.

Отдельно отметьте момент деградации: например, когда p95 TTFT резко растёт, а пропускная способность перестаёт увеличиваться. Это более полезная граница, чем одно максимальное значение токенов в секунду. Сравнивайте также устойчивость: система, которая показывает высокий максимум, но часто вытесняет запросы, может быть хуже для интерактивного сервиса.

Типовые ошибки

Недостаточно видеопамяти при загрузке

Уменьшите длину контекста, выберите подходящую точность или снизьте долю памяти, выделяемую серверу, только если это согласуется с целью эксперимента. Проверьте, что на GPU не остался другой процесс. Не считайте такой запуск нагрузочным результатом: модель должна стабильно стартовать до начала теста.

Пропускная способность растёт, а задержка становится неприемлемой

Это ожидаемый компромисс для многих режимов пакетирования. Смотрите на p95 TTFT и межтокенную задержку отдельно от суммарных токенов в секунду. Для пользовательского API задайте допустимые границы задержки и выбирайте рабочую точку по ним.

Результаты разных запусков не сопоставимы

Проверьте версию образа, модель, параметры семплирования, длины промптов, длительность прогрева, конкурентность и состав фоновых процессов. Изменение любого из этих факторов нужно отражать в отчёте.

Нельзя подтвердить вытеснение по одному графику GPU

Утилизация GPU и занятая память не показывают полный жизненный цикл запроса. Используйте логи vLLM, клиентские таймстемпы, HTTP-статусы и счётчик завершённых запросов. Если конкретная версия сервера не предоставляет нужный счётчик напрямую, помечайте вытеснение как неподтверждённое, а не выводите его из косвенного признака.

Ограничения методики

В исходных данных не приведены конкретная модель, GPU, версия vLLM, профили запросов и измеренные значения. Поэтому эта статья описывает воспроизводимый стенд и форму сравнения, но не заявляет численные результаты. Перед публикацией отчёта добавьте эти параметры и исходные логи.

Синтетическая нагрузка с одинаковыми промптами не отражает полностью реальный трафик. Для production-профиля отдельно моделируйте короткие и длинные контексты, всплески конкурентности, отмену клиентом, неоднородный max_tokens и длительные запросы. Сравнение также нельзя переносить между GPU и версиями vLLM без повторной проверки.

Итог

PagedAttention и vLLM стоит оценивать не по одному показателю памяти или максимальной скорости. Практический ответ даёт связка из четырёх метрик: пропускная способность, TTFT, межтокенная задержка и подтверждённое вытеснение. Запустите сервер с зафиксированной конфигурацией, прогрейте его, пройдите несколько уровней конкурентности и сохраните как агрегаты, так и распределения задержек. Так будет видно, помогает ли управление KV-кэшем именно вашему профилю нагрузки.

Для соседних тем используйте раздел с практическими гайдами и глоссарий терминов.
