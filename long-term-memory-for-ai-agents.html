Практика 12 минут чтения AI-агенты

Долговременная память для AI-агентов: сравниваем закрепление, сжатие и поиск

Длинный диалог сам по себе не превращается в память. Если отправлять модели всю историю, растут стоимость и задержка; если обрезать историю, агент забывает ограничения, решения и незавершённые планы. Рабочая система памяти разделяет три задачи: что нужно сохранить навсегда, что можно сжать и что следует найти по запросу.

В этой статье соберём небольшой воспроизводимый прототип. Он будет хранить закреплённые факты, делать семантическое извлечение записей, сжимать старые сообщения и измерять, насколько хорошо retrieval возвращает нужный контекст. Код ниже — учебный пример архитектуры, а не готовая библиотека.

Почему одной истории диалога недостаточно

У агента есть разные типы информации, и у каждого свой срок жизни:

  • Факты и ограничения: «не отправлять письма без подтверждения», «проект использует Python 3.12». Потеря такой записи может привести к неверному действию.
  • Планы: следующие шаги, открытые вопросы и ожидаемые результаты. Они меняются, поэтому их нельзя хранить без версии или даты.
  • Эпизоды: подробности конкретного разговора. Их обычно достаточно сжать в краткое резюме.
  • Справочный материал: документы и заметки, которые нужно извлекать по смыслу, а не приклеивать к каждому запросу.

Поэтому память лучше моделировать как несколько слоёв, а не как одну бесконечную ленту: 

текущий запрос
      ↓
короткая история + сжатое резюме
      ↓
закреплённые факты и ограничения
      ↓
поиск релевантных эпизодов и документов
      ↓
ответ агента

Три стратегии: закрепление, сжатие и поиск

1. Закрепление

Закрепление — явная запись факта с устойчивым идентификатором, источником, временем и уровнем доверия. Это лучший слой для правил, предпочтений и решений, которые должны пережить очистку истории. 

{
  "id": "fact-001",
  "text": "Перед публикацией требуется ручное подтверждение.",
  "kind": "constraint",
  "source": "conversation:42",
  "confidence": 0.96,
  "updated_at": "2026-11-28T10:00:00Z"
}

Закрепление не означает «верить всему, что сказал пользователь». Перед записью полезно проверить: является ли утверждение долговечным, не противоречит ли оно уже сохранённому факту и разрешено ли агенту самостоятельно его закреплять.

2. Сжатие

Сжатие уменьшает объём старого контекста, сохраняя смысл. Оно подходит для хода обсуждения, списка решений и незавершённых задач. Сжатое резюме должно быть проверяемым: храните исходные идентификаторы сообщений и дату создания.

Плохое резюме стирает неопределённость: «пользователь согласился» вместо «пользователь рассмотрел вариант, но решение не принято». Для агента это уже изменение состояния мира.

3. Поиск

Поиск, или retrieval, выбирает небольшую часть памяти под текущий запрос. Векторный поиск удобен для смыслового сходства, но не заменяет фильтры по типу, владельцу, сроку действия и уровню доступа. На практике полезна гибридная схема: метаданные ограничивают область, а семантический поиск ранжирует кандидатов.

Минимальная модель данных

Для прототипа достаточно JSONL-файла. Одна строка — одна запись памяти. Такое хранилище легко просматривать, версионировать и заменять на базу данных позже. 

memory/
  facts.jsonl
  episodes.jsonl
  summaries.jsonl
  eval.jsonl

Минимальные поля:

{
  "id": "mem-001",
  "text": "Краткое содержание записи",
  "type": "fact|episode|summary",
  "tags": ["project", "constraint"],
  "status": "active|superseded|expired",
  "source_ids": ["msg-17"],
  "created_at": "2026-11-28T10:00:00Z",
  "expires_at": null
}

Поле status важно для исправлений. Не удаляйте старый факт молча: пометьте его как superseded и укажите новую запись. Это помогает расследовать, почему агент принял конкретное решение.

Воспроизводимый прототип

Ниже — безопасная последовательность для локального эксперимента. Команды создают отдельную папку и не изменяют системные файлы. 

mkdir -p agent-memory-prototype/memory
cd agent-memory-prototype
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install scikit-learn

Создайте файл memory_demo.py и добавьте простой TF-IDF retrieval. Это не полноценный production-векторный индекс, а прозрачная контрольная точка для проверки идеи: 

from dataclasses import dataclass
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

@dataclass
class Memory:
    id: str
    text: str
    kind: str
    status: str = "active"

memories = [
    Memory("f-1", "Перед публикацией требуется ручное подтверждение.", "fact"),
    Memory("f-2", "Проект использует Python 3.12.", "fact"),
    Memory("e-1", "Обсуждали перенос фоновых задач на отдельный worker.", "episode"),
    Memory("s-1", "Следующий шаг: подготовить проверяемый прототип retrieval.", "summary"),
]

active = [m for m in memories if m.status == "active"]
vectorizer = TfidfVectorizer(ngram_range=(1, 2))
matrix = vectorizer.fit_transform([m.text for m in active])

def retrieve(query: str, top_k: int = 3):
    query_vector = vectorizer.transform([query])
    scores = cosine_similarity(query_vector, matrix)[0]
    ranked = sorted(
        zip(active, scores),
        key=lambda pair: pair[1],
        reverse=True
    )
    return [(memory.id, round(float(score), 3), memory.text)
            for memory, score in ranked[:top_k]]

if __name__ == "__main__":
    print(*retrieve("Что нужно сделать перед публикацией?"), sep="\\n")

Запустите только локальный пример:

python memory_demo.py

В production-системе вместо TF-IDF можно использовать эмбеддинги и векторную базу, но интерфейс лучше сохранить тем же: на вход подаются запрос и фильтры, на выходе — записи, оценки и их источники.

Как сжимать контекст без потери ограничений

Сжатие следует выполнять не одним общим промптом, а по схеме с обязательными полями. Например: 

Сформируй JSON:
{
  "decisions": [],
  "open_questions": [],
  "constraints": [],
  "next_actions": [],
  "uncertainties": []
}

Правила:
1. Не превращай предположение в факт.
2. Сохраняй отрицания и условия.
3. Для каждого пункта укажи id исходного сообщения.
4. Если решение не принято, запиши это явно.

После генерации резюме примените механическую проверку: все ограничения из последнего окна должны либо попасть в новое резюме, либо иметь объяснение, почему они устарели. Если модель не уверена, лучше оставить запись в исходной истории и повторить сжатие позже.

Проверка качества retrieval

Качество поиска нельзя оценивать впечатлением от одного ответа. Соберите небольшой набор запросов, где заранее указаны правильные записи. Это не «тест клиентов» и не внешнее измерение, а локальная проверка вашего прототипа. 

[
  {
    "query": "Что нужно сделать перед публикацией?",
    "relevant_ids": ["f-1"]
  },
  {
    "query": "Какой следующий шаг по памяти агента?",
    "relevant_ids": ["s-1"]
  }
]

Для каждого запроса посчитайте Recall@k: была ли хотя бы одна релевантная запись среди первых k результатов. Затем отдельно проверьте точность контекста вручную: найденная запись может быть похожей по словам, но не отвечать на вопрос. 

Recall@k =
число запросов, где релевантная запись попала в top-k
/
общее число запросов

Добавьте негативные запросы: для них retrieval должен вернуть пустой результат или записи с низким score. Это защищает от привычки агента уверенно достраивать ответ по слабому совпадению.

Сборка конвейера памяти

Практический цикл можно описать так:

  1. Получить новое сообщение и текущую задачу.
  2. Выделить потенциальные факты, ограничения, планы и эпизоды.
  3. Проверить кандидатов на дубликаты и противоречия.
  4. Закрепить только записи, прошедшие политику доверия.
  5. Сжать старую часть диалога с сохранением источников.
  6. Выполнить retrieval с фильтрами доступа и срока действия.
  7. Показать модели найденные записи вместе с их id, типом и датой.
  8. Записать, какие записи были использованы в ответе.

Последний пункт превращает память в наблюдаемую систему. Если ответ оказался неверным, можно проверить не только генерацию, но и весь путь: запись не сохранилась, не нашлась, была неправильно ранжирована или была проигнорирована моделью.

Типовые ошибки

  • Сохранять всю историю. Объём растёт, а важность записей не различается.
  • Считать сходство доказательством. Высокий score не подтверждает истинность факта.
  • Не учитывать свежесть. Старое предпочтение может быть заменено новым.
  • Смешивать пользователей и проекты. Каждый запрос должен иметь область видимости и фильтр доступа.
  • Удалять противоречивые записи. Для аудита лучше использовать версии и статусы.
  • Не измерять пустые ответы. Иногда безопаснее не найти память, чем вернуть нерелевантную.

Ограничения прототипа

TF-IDF не понимает смысл так, как современные embedding-модели, JSONL не решает конкурентную запись, а простая проверка Recall@k не измеряет фактическую полезность ответа. Для реальной системы потребуются контроль доступа, шифрование, политика удаления, дедупликация, обработка персональных данных, мониторинг задержки и тесты на prompt injection в сохранённых записях.

Начинайте с малого: закрепите несколько критичных ограничений, добавьте retrieval с источниками, затем измерьте ошибки на собственном наборе запросов. После этого станет понятно, нужна ли вам более сложная база, reranker или отдельный сервис сжатия.

Итог

Долговременная память AI-агента — это не бесконечный контекст. Закрепление защищает важные факты, сжатие удерживает ход работы в компактной форме, а поиск подбирает нужные записи именно в момент запроса. Надёжность появляется на границе этих механизмов: у каждой записи есть источник и срок жизни, у retrieval есть измеримые метрики, а у агента — возможность не использовать память, если уверенности недостаточно.

Для продолжения работы откройте практические гайды и сверяйтесь с глоссарием терминов.
