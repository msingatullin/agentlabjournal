Архитектура автоматизаций

От n8n к LangGraph: когда автоматизации нужна инженерная архитектура

Уровень: средний Время чтения: до 12 минут Практический разбор

Low-code-сценарий удобен, пока процесс можно объяснить несколькими связными шагами. Когда появляются ветвления, повторы, долгоживущая память и требования к восстановлению, граф в интерфейсе перестаёт быть достаточной архитектурой.

Короткий ответ

Переносить сценарий из n8n в код стоит не потому, что код «профессиональнее». Причина должна быть практической: процесс трудно тестировать, его состояние смешано с побочными эффектами, ошибки требуют ручного разбора, а изменение одного узла неожиданно влияет на весь маршрут.

В этом случае n8n можно оставить на границах системы — для webhook, расписания, уведомлений и простых интеграций, — а центральную логику вынести в приложение. LangGraph подходит для процессов, которые естественно описываются как граф состояний: узлы выполняют действия, переходы выбирают следующий шаг, а состояние передаётся между итерациями.

Где заканчивается удобный сценарий n8n

n8n хорошо показывает линейную последовательность: получить событие, преобразовать данные, вызвать API, отправить результат. Такая схема остаётся прозрачной, пока каждый шаг имеет один очевидный вход и один ожидаемый выход.

Сложность начинается, когда визуальный workflow начинает выполнять роль сразу нескольких слоёв:

  • бизнес-правил и маршрутизации;
  • хранилища состояния;
  • повторных попыток и компенсаций;
  • интеграционных вызовов;
  • логирования и ручного восстановления.

Сам по себе большой workflow не является проблемой. Проблема — отсутствие ясной границы ответственности. Если для ответа на вопрос «почему заявка оказалась на этом шаге?» нужно просматривать десятки соединений и скрытых выражений, процесс уже нуждается в инженерном описании.

Критерии миграции

Используйте критерии как чек-лист, а не как формулу. Один признак редко оправдывает перенос, но несколько повторяющихся сигналов обычно показывают, что пора менять центр архитектуры.

1. Ветвления стали основным содержанием процесса

Если маршрут зависит от множества условий, а ветки могут возвращаться к предыдущим шагам, граф становится труднее читать в редакторе. В коде правила можно назвать, сгруппировать и покрыть тестами.

2. Сценарию нужно долгоживущее состояние

Одно выполнение может продолжаться после паузы, ручного решения или внешнего события. Тогда важно явно определить, что хранится между шагами: идентификатор процесса, входные данные, результаты проверок, ошибки и версия маршрута.

3. Повторный запуск должен быть безопасным

Сетевой сбой может произойти после успешной записи во внешнюю систему. Повторная попытка должна понимать, была ли операция выполнена. Если идемпотентность спрятана в отдельных выражениях n8n, риск трудно оценить и воспроизвести.

4. Ошибки требуют разных стратегий

Временная ошибка API, некорректные входные данные и отказ бизнес-правила — разные классы проблем. Для них нужны разные действия: повторить, остановить, отправить на ручную проверку или продолжить по альтернативной ветке.

5. Изменения стали опасными

Если небольшое изменение в одном узле заставляет вручную проверять весь сценарий, стоимость поддержки уже выше стоимости явных интерфейсов и автоматических тестов.

6. Нужны наблюдаемость и воспроизводимость

Для расследования необходимо видеть вход процесса, переходы между узлами, версии правил, внешние вызовы и итоговое состояние. Истории запусков бывает недостаточно, если она не связана с доменной моделью процесса.

Главное правило: разделяйте состояние и эффекты

Наиболее полезный шаг перед миграцией — провести границу между чистой логикой и побочными эффектами. Состояние описывает, что система знает. Эффект меняет внешний мир: отправляет запрос, создаёт запись, публикует сообщение или вызывает оплату. 

{
  "case_id": "пример-123",
  "input": {
    "text": "Входное сообщение"
  },
  "decision": {
    "category": "unknown",
    "needs_review": false
  },
  "artifacts": [],
  "status": "received",
  "last_error": null
}

Это пример структуры, а не универсальная схема данных. Важно, чтобы состояние можно было сериализовать, проверить и восстановить. Оно не должно содержать открытые соединения, объекты SDK или неявные ссылки на интерфейс n8n.

Узел графа должен по возможности принимать состояние и возвращать обновление состояния. Вызов внешнего API лучше вынести в отдельную функцию с понятным контрактом, таймаутом, журналированием и политикой повторов. 

def classify(state):
    category = classify_text(state["input"]["text"])
    return {
        "decision": {
            **state["decision"],
            "category": category
        },
        "status": "classified"
    }

def route(state):
    if state["decision"]["needs_review"]:
        return "human_review"
    return "continue"

Такой код иллюстрирует идею разделения. Реальная реализация может отличаться: в частности, модель, хранилище и формат сообщений выбираются под конкретный процесс.

Почему здесь появляется LangGraph

LangGraph удобно рассматривать не как замену всем функциям n8n, а как слой оркестрации для состояния и переходов. В нём можно выразить узлы процесса, условную маршрутизацию, циклы и точки остановки. Это полезно там, где маршрут является частью логики продукта, а не только последовательностью интеграционных действий.

Однако LangGraph не решает автоматически вопросы доменной модели, доступа, идемпотентности, секретов и качества внешних сервисов. Эти обязанности остаются у приложения и его инфраструктуры.

Схема постепенного переноса ядра

Шаг 1. Зафиксируйте текущий контракт

Опишите вход, выход, обязательные поля, возможные статусы и внешние эффекты. Не начинайте с переписывания узлов. Сначала нужно понять, что именно считается успешным завершением и какие операции нельзя выполнить дважды.

Шаг 2. Оставьте n8n входной точкой

Webhook или расписание могут по-прежнему запускать процесс. Передавайте в новое приложение минимальный пакет: идентификатор выполнения, входные данные и корреляционный идентификатор. Не копируйте в него весь внутренний контекст n8n.

Шаг 3. Вынесите одну чистую ветку

Выберите участок без критического побочного эффекта: нормализацию, классификацию или проверку обязательных полей. Сделайте его функцией с явным входом и выходом, а затем сравните результат с текущим сценарием.

Шаг 4. Перенесите маршрутизацию

Когда чистая ветка стабилизировалась, перенесите условия переходов. n8n может передавать выполнение в приложение и получать следующий статус, пока старые интеграционные узлы работают без изменений.

Шаг 5. Оберните эффекты идемпотентными операциями

Для каждой записи или отправки определите ключ идемпотентности. Перед повторной операцией приложение должно проверить, не был ли эффект уже применён. Внешний API может поддерживать собственный ключ, а при его отсутствии проверка должна быть реализована на вашей стороне.

Шаг 6. Переведите запуск под управление приложения

После проверки переходов и эффектов n8n можно оставить адаптером: он принимает событие и вызывает endpoint приложения. Позже расписание, уведомления или простые административные действия можно вернуть в n8n, если так удобнее команде.

Воспроизводимый минимальный эксперимент

Ниже — безопасный локальный скелет проверки идеи. Команды создают отдельную папку и виртуальное окружение; они не обращаются к внешним API и не требуют секретов. 

mkdir -p langgraph-migration-demo
cd langgraph-migration-demo
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install langgraph

Создайте файл main.py с минимальным графом состояния: 

from typing import TypedDict
from langgraph.graph import END, START, StateGraph

class State(TypedDict):
    text: str
    category: str
    status: str

def classify(state: State):
    text = state["text"].lower()
    category = "urgent" if "срочно" in text else "regular"
    return {"category": category, "status": "classified"}

def finish(state: State):
    return {"status": f"finished:{state['category']}"}

graph = StateGraph(State)
graph.add_node("classify", classify)
graph.add_node("finish", finish)
graph.add_edge(START, "classify")
graph.add_edge("classify", "finish")
graph.add_edge("finish", END)

app = graph.compile()
result = app.invoke({
    "text": "Проверить заявку",
    "category": "",
    "status": "received"
})
print(result)

Запустите пример: 

python main.py

Ожидаемый результат — словарь с категорией regular и статусом finished:regular. Это не готовая production-система, а проверка того, что состояние проходит через узлы и изменяется предсказуемо.

Проверка результата миграции

Проверяйте не только то, что новый граф «работает». Сравните поведение старого и нового маршрутов на одинаковых входах.

  • одинаковый вход даёт одинаковый итоговый статус;
  • ошибка внешнего сервиса не теряет состояние процесса;
  • повторный запуск не создаёт дубликат эффекта;
  • каждый переход можно связать с идентификатором выполнения;
  • ручная остановка и продолжение имеют определённый контракт;
  • секреты не попадают в состояние, логи и входные данные узлов.

Для локальной проверки полезно начать с таблицы сценариев: обычный вход, пустое обязательное поле, временная ошибка, повторный запуск и ручная остановка. Таблица должна описывать ожидаемый статус и разрешённые внешние эффекты.

Типовые ошибки

Переписать весь workflow за один раз

Такой перенос затрудняет сравнение и увеличивает область отказа. Переносите сначала состояние и чистые правила, затем маршрутизацию и только потом эффекты.

Сделать граф копией визуального редактора

Если каждый визуальный узел превращается в отдельную функцию без пересмотра контрактов, сложность сохраняется. Перенос должен убрать скрытые зависимости, а не только изменить способ отображения.

Хранить в состоянии слишком много

Полные ответы внешних систем, секреты и временные объекты делают состояние хрупким. Храните только данные, необходимые для продолжения и аудита; большие артефакты выносите в отдельное хранилище.

Добавить повторы без идемпотентности

Повтор — это не универсальное исправление. Если операция могла завершиться успешно, но ответ потерялся, повтор без ключа идемпотентности может создать дубликат.

Считать LangGraph системой надёжности

Оркестратор помогает описывать процесс, но не заменяет мониторинг, хранилище, контроль доступа, резервирование и правила работы с внешними API.

Ограничения подхода

Миграция в код увеличивает требования к тестированию, релизам, наблюдаемости и ответственности за инфраструктуру. Для короткого процесса с несколькими шагами n8n может быть более дешёвым по времени сопровождения.

Не всякий процесс с LLM требует графа. Если задача сводится к одному вызову модели и простой проверке результата, достаточно обычного сервиса. LangGraph оправдан тогда, когда есть управляемое состояние, несколько переходов, повторяемость или необходимость продолжить процесс после паузы.

Итог

Решение «от n8n к LangGraph» стоит принимать по сложности управления процессом, а не по моде на инструменты. Оставьте n8n там, где он хорошо работает как слой входов и интеграций. Вынесите ядро в код, когда вам нужны явное состояние, проверяемые переходы, безопасные повторы и воспроизводимое восстановление.

Самая безопасная стратегия — постепенная: зафиксировать контракт, вынести чистую логику, перенести маршрутизацию, защитить эффекты идемпотентностью и только затем менять точку управления процессом.
