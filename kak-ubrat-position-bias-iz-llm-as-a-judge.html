Как измерить и уменьшить position bias в LLM-as-a-judge

Продвинутый уровень До 12 минут Практический стенд

Position bias — это систематическое предпочтение ответа из-за его позиции в запросе, а не из-за качества. В парном сравнении проблема проявляется особенно неприятно: модель выбирает ответ A, но после простой перестановки тех же ответов выбирает уже ответ B.

Ниже — минимальный тестовый стенд без привязки к конкретному провайдеру. Он дважды отправляет одну и ту же пару ответов: сначала в порядке A/B, затем в порядке B/A. Если итоговое предпочтение не сохраняется, пара считается спорной и превращается в ничью. Это позволяет не выдавать нестабильный вердикт за надёжный сигнал качества.

Что именно измеряем

Пусть судья сравнивает ответы a и b. Обозначим его решение в исходном порядке как r₁, а решение после перестановки — как r₂. После восстановления исходных имён ответов получаем четыре случая:

Исходный вердикт Вердикт после перестановки Итог
A лучше B A лучше B Стабильная победа A
B лучше A B лучше A Стабильная победа B
A лучше B B лучше A Переворот, итог — ничья
Ничья Любой результат Ничья

Основная диагностическая метрика — доля переворотов среди пар, где оба запуска дали противоположные строгие вердикты:

flip_rate = число переворотов / число пар с двумя строгими вердиктами

Для принятия решений полезнее смотреть не только на среднее значение, но и на разрезы: по типу задания, длине ответа, языку, модели-судье и температуре. Смешивание всех пар в одну цифру может скрыть bias только на длинных или только на англоязычных ответах.

Формат входных данных

Создайте файл pairs.jsonl. Одна строка — одна пара ответов. Поле id нужно для трассировки, а criteria должно содержать те же критерии, которые используются в вашей реальной оценке. 

{"id":"case-001","question":"Объясните идемпотентность HTTP-запросов.","criteria":["точность","полнота","ясность"],"a":"Идемпотентный запрос можно повторить без дополнительного изменения результата на сервере.","b":"Идемпотентность означает, что запрос всегда выполняется быстрее при повторе."}
{"id":"case-002","question":"Предложите способ проверить утечку данных в логах.","criteria":["безопасность","практичность","полнота"],"a":"Нужно искать секреты по регулярным выражениям и проверить выборку логов вручную.","b":"Нужно определить источники логов, применить обнаружение секретов, проверить false positive и ограничить доступ к результатам."}

Контракт адаптера судьи

Чтобы стенд не зависел от SDK конкретной модели, вынесем вызов судьи в отдельную команду. Стенд передаёт ей JSON через стандартный ввод. Адаптер обязан вернуть один JSON-объект: 

{"winner":"A","reason":"Короткое обоснование"}
{"winner":"B","reason":"Короткое обоснование"}
{"winner":"tie","reason":"Ответы сопоставимы или различие недостаточно убедительно"}

Значение winner должно быть ровно одним из A, B или tie. В промпте адаптера важно явно объяснить, что A и B — это метки текущих позиций, а не постоянные имена кандидатов.

Стенд перестановки

Сохраните следующий файл как position_bias_check.py. Он не выполняет shell-команду через оболочку: команда разбирается через shlex.split, а запуск идёт с ограничением времени. Это снижает риск случайного исполнения содержимого входного файла. 

#!/usr/bin/env python3
import argparse
import json
import shlex
import subprocess
import sys
from pathlib import Path


def run_judge(command, payload, timeout):
    completed = subprocess.run(
        command,
        input=json.dumps(payload, ensure_ascii=False) + "\n",
        text=True,
        capture_output=True,
        timeout=timeout,
        check=False,
    )

    if completed.returncode != 0:
        raise RuntimeError(
            f"judge exited with {completed.returncode}: "
            f"{completed.stderr.strip()}"
        )

    try:
        result = json.loads(completed.stdout)
    except json.JSONDecodeError as exc:
        raise RuntimeError("judge returned invalid JSON") from exc

    winner = result.get("winner")
    if winner not in {"A", "B", "tie"}:
        raise RuntimeError("winner must be A, B or tie")

    return winner


def make_prompt(pair, first, second):
    criteria = "\n".join(f"- {item}" for item in pair["criteria"])

    return {
        "system": (
            "Ты строгий pairwise-judge. Сравни два ответа только по вопросу "
            "и критериям. Не используй позицию ответа как аргумент. "
            "Верни JSON с winner: A, B или tie."
        ),
        "question": pair["question"],
        "criteria": criteria,
        "answer_A": first,
        "answer_B": second,
    }


def restore_original_labels(winner_after_swap):
    if winner_after_swap == "A":
        return "B"
    if winner_after_swap == "B":
        return "A"
    return "tie"


def evaluate_pair(pair, command, timeout):
    first = run_judge(
        command,
        make_prompt(pair, pair["a"], pair["b"]),
        timeout,
    )

    swapped = run_judge(
        command,
        make_prompt(pair, pair["b"], pair["a"]),
        timeout,
    )

    second_in_original_labels = restore_original_labels(swapped)

    if first == "tie" or second_in_original_labels == "tie":
        outcome = "tie"
        flip = False
    elif first == second_in_original_labels:
        outcome = first
        flip = False
    else:
        outcome = "tie"
        flip = True

    return {
        "id": pair["id"],
        "first": first,
        "after_swap_in_original_labels": second_in_original_labels,
        "outcome": outcome,
        "flip": flip,
    }


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("input", type=Path)
    parser.add_argument("--judge-cmd", required=True)
    parser.add_argument("--timeout", type=float, default=60)
    args = parser.parse_args()

    command = shlex.split(args.judge_cmd)
    results = []
    strict_pairs = 0
    flips = 0

    with args.input.open(encoding="utf-8") as stream:
        for line_number, line in enumerate(stream, start=1):
            if not line.strip():
                continue

            try:
                pair = json.loads(line)
                result = evaluate_pair(pair, command, args.timeout)
            except Exception as exc:
                print(
                    f"line {line_number}: {exc}",
                    file=sys.stderr,
                )
                raise SystemExit(1)

            results.append(result)

            if result["first"] != "tie" and (
                result["after_swap_in_original_labels"] != "tie"
            ):
                strict_pairs += 1

            if result["flip"]:
                flips += 1

    for result in results:
        print(json.dumps(result, ensure_ascii=False))

    flip_rate = flips / strict_pairs if strict_pairs else 0.0
    summary = {
        "pairs": len(results),
        "strict_pairs": strict_pairs,
        "flips": flips,
        "flip_rate": round(flip_rate, 4),
        "stable_or_tie_outcomes": sum(
            result["outcome"] in {"A", "B", "tie"}
            for result in results
        ),
    }

    print(
        json.dumps({"summary": summary}, ensure_ascii=False),
        file=sys.stderr,
    )


if __name__ == "__main__":
    main()

Как запустить проверку

Команда ниже предполагает, что рядом находится ваш адаптер judge_adapter.py, который читает один JSON из stdin и печатает один JSON в stdout. 

python3 position_bias_check.py pairs.jsonl \
  --judge-cmd "python3 judge_adapter.py" \
  --timeout 60

Результаты по парам будут выведены в stdout. Итоговая строка появится в stderr и выглядит примерно так: 

{"summary":{"pairs":2,"strict_pairs":2,"flips":1,"flip_rate":0.5,"stable_or_tie_outcomes":2}}

Это иллюстрация формата, а не измеренный результат конкретной модели. В реальном запуске число зависит от набора пар, промпта, параметров генерации и реализации адаптера.

Как интерпретировать результат

Нулевая доля переворотов не доказывает отсутствие position bias: судья может стабильно выбирать первый ответ, если пары случайно устроены так, что первый действительно чаще лучше. Поэтому перестановку нужно сочетать с независимой проверкой качества и с балансировкой данных.

Практическая диагностика выглядит так:

  • сравните долю побед A и B в исходном порядке;
  • посмотрите flip rate по категориям задач;
  • проверьте, не растёт ли нестабильность на длинных ответах;
  • сравните вердикты с человеческой разметкой на небольшой контрольной выборке;
  • отдельно посчитайте долю ничьих после применения правила перестановки.

Если A выигрывает заметно чаще B, а при перестановке появляется много переворотов, это сильный сигнал позиционной зависимости. Если переворотов мало, но корреляция с человеческой оценкой низкая, проблема, вероятно, не в позиции, а в критериях, промпте или способности судьи оценивать предметную область.

Как уменьшить position bias

1. Делайте обязательную перестановку

Для каждой пары запускайте обе конфигурации и агрегируйте только восстановленные исходные метки. Один запуск дешевле, но он не позволяет отличить качество ответа от эффекта позиции.

2. Используйте симметричный промпт

Не называйте варианты «эталонным» и «кандидатским», если это не отражает вашу задачу. Формулировки должны быть одинаковыми для A и B. Критерии лучше перечислять до ответов, чтобы судья применял их к обоим вариантам.

3. Запрещайте аргумент «первый лучше»

Это не устранит bias само по себе, но уменьшит вероятность, что модель легализует его в объяснении. В адаптере требуйте сначала внутренне сравнить ответы по критериям, а затем вернуть структурированный результат.

4. Считайте спорные пары ничьёй

Если строгий вердикт меняется после перестановки, не выбирайте победителя случайным образом. Ничья честнее: она сохраняет информацию о нестабильности и не загрязняет рейтинг кандидатов ложным преимуществом.

5. Не полагайтесь на объяснение как на доказательство

Судья может привести убедительную причину уже после случайного выбора. Анализируйте структурированное поле winner, а объяснения используйте для аудита отдельных случаев.

6. Контролируйте генерацию

Зафиксируйте модель, версию промпта, температуру и остальные параметры. При наличии seed сохраните его, но не считайте детерминированность доказательством корректности: одинаково воспроизводимая ошибка всё равно остаётся ошибкой.

Типовые ошибки

  • Неправильное восстановление меток. После swap победитель A означает победу исходного B, а победитель B — исходного A.
  • Смешивание ничьих и переворотов. Ничья в одном из запусков — это неопределённость, а не строгий flip.
  • Одинаковый текст ответа в обеих позициях. Такие пары не тестируют позиционную зависимость.
  • Неравноценные пары. Если один ответ очевидно лучше почти во всех случаях, отсутствие переворота ничего не говорит о тонком bias.
  • Промпт, раскрывающий правильный ответ. Если в нём есть фразы вроде «проверь, почему A лучше», тест становится односторонним.
  • Оценка только по средней доле побед. Нужны перевороты, ничьи и разрезы по подгруппам.
  • Безлимитный вызов адаптера. Устанавливайте timeout и обрабатывайте невалидный JSON, чтобы один сбой не создавал бесконечный процесс.

Ограничения метода

Парная перестановка измеряет чувствительность к позиции, но не доказывает объективность судьи. Она не заменяет эталонную разметку, проверку фактической точности и анализ соответствия критериям. При высокой случайности модель может давать разные ответы даже без выраженного position bias, поэтому полезно повторять проверку на нескольких независимых запусках.

Ничья также не всегда означает, что ответы равноценны. В этом стенде она означает более узкое утверждение: по наблюдаемому поведению судьи нельзя надёжно выбрать победителя после перестановки.

Минимальный чек-лист перед публикацией метрики

  1. Входные пары сбалансированы по порядку и покрывают реальные типы задач.
  2. Адаптер возвращает только допустимые значения A, B или tie.
  3. После swap метки корректно возвращаются к исходным ответам.
  4. Перевороты считаются отдельно от обычных ничьих.
  5. Сохраняются модель, промпт, параметры и версия стенда.
  6. В отчёте есть общий результат и разрезы по важным подгруппам.
  7. Спорные пары не превращаются в случайного победителя.
