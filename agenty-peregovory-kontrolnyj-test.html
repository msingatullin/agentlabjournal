Контроль качества агентных систем

Когда агенты торгуются друг с другом: как провести контрольный тест

Уровень: продвинутый Время чтения: до 12 минут Результат: воспроизводимый парный тест

Если один агент представляет вашу компанию, а другой — контрагента, итог переговоров зависит не только от модели, промпта и бизнес-правил. Ваша система может уступать там, где другая сторона не просила уступки, слишком рано соглашаться или тратить больше времени и токенов, чем оправдывает сделка. Проверить это можно не впечатлениями, а парным тестом с контрольной группой.

В этой статье контрфактический сценарий — это заранее зафиксированный вариант тех же переговоров, в котором меняется только выбранный агент. Это позволяет отделить эффект агента от влияния цены, состава запроса, случайного порядка реплик и других факторов.

Что именно нужно измерить

Вопрос «какой агент лучше торгуется?» слишком расплывчат. Для контрольного теста заранее определите, что считается потерей и какой компромисс допустим. Минимальный набор метрик:

  • Стоимость сделки — денежный результат для вашей стороны после всех уступок, комиссий, скидок и иных заранее известных компонентов.
  • Качество результата — выполнение обязательных условий, сроков, объёма и ограничений.
  • Цена переговоров — время выполнения, число ходов, количество вызовов инструментов и расход токенов, если эти показатели значимы для экономики системы.
  • Риск — нарушения политики, раскрытие запрещённых данных, несанкционированные обещания и выход за лимиты полномочий.

Основной показатель должен быть один. Например, это может быть итоговая маржа при условии, что обязательные ограничения не нарушены. Остальные показатели используйте как ограничения и объясняющие факторы. Иначе агент, который дал более дешёвую сделку, может ошибочно оказаться победителем, хотя нарушил обязательное условие.

Дизайн теста: одна пара, два варианта

Сформируйте набор переговорных задач и повторите каждую задачу минимум в двух вариантах: с агентом A и с агентом B на вашей стороне. Агент на другой стороне должен оставаться неизменным. Если тестируете не своего, а внешнего агента, зафиксируйте и его версию, настройки и доступные инструменты.

  1. Составьте обезличенный набор задач из реальных или синтетических сценариев. Каждый сценарий должен иметь одинаковый формат входных данных.
  2. Для каждой задачи зафиксируйте резервный результат, минимально приемлемые условия, запрещённые уступки и лимит полномочий агента.
  3. Разделите сценарии на пары. Внутри пары одинаковые входные данные, а порядок запуска определите случайно.
  4. Случайно назначьте вариант A или B первым. Порядок важен: второй запуск может получить преимущество из-за кэширования, состояния среды или повторного использования контекста.
  5. Сохраните версии модели, системных инструкций, инструментов, схем данных и параметров генерации.
  6. Проведите оба запуска в изолированной среде. Не разрешайте первому запуску менять данные, доступные второму.

Если переговоры недетерминированы, одного запуска на сценарий недостаточно. Повторяйте каждую пару несколько раз с разными seed или другими разрешёнными настройками случайности. Число повторов должно быть установлено до просмотра результатов. Иначе команда рискует выбрать удобное количество запусков постфактум.

Контрольная группа и честное сравнение

Контрольная группа нужна, чтобы понять, не изменился ли сам процесс переговоров независимо от агента. Это может быть текущая рабочая версия агента, ручной эталонный процесс или заранее утверждённая базовая стратегия. Выберите один вариант и не меняйте его во время эксперимента.

Практическая схема выглядит так:

Группа Что меняется Зачем нужна
Контрольная Ничего, используется текущая базовая стратегия Показывает обычный уровень результата
Тестовая A Только агент на вашей стороне Измеряет эффект варианта A
Тестовая B Только агент на вашей стороне Измеряет эффект варианта B

Если обе стороны переговоров принадлежат вашей компании, не меняйте их одновременно в одном сравнении. Иначе будет невозможно понять, какой агент создал разницу. Для отдельного исследования можно провести факторный тест, но это уже другой дизайн эксперимента и больший объём данных.

Логирование: записывайте не только финальную цену

Финальный результат не объясняет, почему возникла потеря. Для каждого запуска сохраняйте структурированную запись: 

{
  "run_id": "локальный идентификатор",
  "scenario_id": "идентификатор сценария",
  "group": "control|A|B",
  "agent_version": "зафиксированная версия",
  "opponent_version": "зафиксированная версия",
  "seed": "если используется",
  "messages": [
    {
      "turn": 1,
      "speaker": "agent|opponent",
      "content": "текст или безопасная ссылка на запись",
      "tool_calls": [],
      "timestamp": "время запуска"
    }
  ],
  "outcome": {
    "deal_value": 0,
    "required_conditions_met": true,
    "policy_violations": 0,
    "turn_count": 0,
    "token_cost": 0
  }
}

В рабочем журнале не храните секреты, токены доступа и лишние персональные данные. Перед записью маскируйте идентификаторы клиентов, платёжные реквизиты и содержимое, которое не требуется для анализа. Отдельно логируйте события отказа, остановки по лимиту и вызовы инструментов: именно там часто обнаруживается скрытая стоимость.

Безопасный запуск

Команды ниже — шаблон локальной проверки. Имена файлов и параметры замените на свои. Они не отправляют запросы во внешние системы, а запускают заранее подготовленный тестовый раннер в режиме симуляции. 

# Проверить, что конфигурация не содержит секретов
rg -n --hidden -g '!*.lock' -g '!node_modules' \
  '(API_KEY|TOKEN|SECRET|PASSWORD|BEGIN PRIVATE KEY)' configs/

# Проверить входные сценарии без запуска переговоров
python -m negotiation_test validate \
  --scenarios scenarios/negotiations.jsonl \
  --policy policies/negotiation.yaml

# Запустить контрольную и тестовые группы в симуляторе
python -m negotiation_test run \
  --scenarios scenarios/negotiations.jsonl \
  --groups control,A,B \
  --mode dry-run \
  --output runs/$(date +%Y%m%d-%H%M%S)

# Сверить число запусков и обязательные поля
python -m negotiation_test verify \
  --input runs/latest \
  --require scenario_id,group,agent_version,outcome

Если раннер поддерживает сетевой доступ, отключите его на этапе отладки или используйте тестовые endpoint’ы. Не подставляйте реальные ключи в командную строку: они могут попасть в историю shell или журналы CI. Перед любым тестом с реальными последствиями добавьте аварийный лимит расходов, ручное подтверждение и возможность остановить очередь.

Как посчитать стоимость сделки

Для каждого запуска используйте одну и ту же формулу. В простом случае: 

net_value =
  gross_value
  - explicit_discount
  - transaction_cost
  - expected_failure_cost
  - agent_operation_cost

Это не универсальная бухгалтерская формула, а каркас измерения. Состав полей зависит от вашей модели бизнеса. Важно, чтобы правила расчёта были утверждены до сравнения и применялись одинаково к контрольной и тестовым группам.

Пример ниже условный: числа не являются результатом реального теста. Если контрольная версия дала 100 условных единиц, а вариант A — 96 при одинаковом качестве и меньших операционных затратах, разницу нельзя автоматически считать эффектом агента. Сначала проверьте доверительный интервал, нарушения ограничений и соответствие сценариев. Если вариант A дал 96 из-за одной запрещённой уступки, это не «дешёвая сделка», а невалидный результат.

Проверка результата

После запуска проверьте данные в следующем порядке:

  1. Полнота: у каждой пары есть контрольный и тестовый запуск, а число повторов одинаково.
  2. Сопоставимость: вход, агент на другой стороне, лимиты, доступные инструменты и параметры среды совпадают.
  3. Валидность: исключены запуски с ошибкой инфраструктуры, обрывом контекста и нарушением протокола.
  4. Ограничения: отдельно посчитаны сделки, нарушившие обязательные условия.
  5. Разница: сравнивается парная разница по одному и тому же сценарию, а не только средние значения всех запусков.
  6. Устойчивость: вывод сохраняется при удалении единичных выбросов и при раздельном анализе подгрупп.

Для каждой пары рассчитайте Δ = результат тестового агента − результат контрольного агента. Покажите медиану, среднее, разброс, долю невалидных сделок и доверительный интервал, если объём данных это позволяет. Не объявляйте агента лучше только потому, что среднее значение выше: один крупный выигрыш может скрыть регулярные небольшие уступки.

Типовые ошибки

  • Меняется сразу несколько компонентов. Новый промпт, модель и набор инструментов не позволяют приписать эффект одному агенту.
  • Нет базовой линии. Без контрольной группы непонятно, улучшился ли результат относительно текущего процесса.
  • Сравниваются разные сценарии. Сложность задачи должна быть одинаковой внутри пары.
  • Логируется только финальная цена. Без истории реплик невозможно найти раннюю необязательную уступку.
  • Победа по деньгам перекрывает нарушение политики. Нарушенные ограничения должны делать запуск невалидным или получать заранее определённый штраф.
  • Результат смотрят до фиксации правил. Метрики и критерии успеха определяйте до запуска.
  • Переговоры повторно используют состояние. Очищайте память, кэш и контекст между запусками.

Ограничения метода

Парный тест измеряет поведение в выбранном наборе сценариев, а не «истинную силу» агента вообще. Синтетические задачи могут не отражать реальную мотивацию контрагента, а реальные переговоры могут содержать факторы, которые невозможно безопасно воспроизвести. Результат также зависит от версии модели, формата контекста, доступных инструментов и политики остановки.

Поэтому итог формулируйте узко: «в этих сценариях, при этих версиях и этих ограничениях агент B показал такую-то парную разницу относительно контрольной группы». Повторяйте тест после существенных изменений и не переносите вывод на новые типы сделок без отдельной проверки.

Критерий решения

Агент можно рекомендовать к следующему этапу только если он одновременно улучшает основной показатель, не увеличивает недопустимый риск, укладывается в операционный бюджет и показывает устойчивый результат на повторных запусках. Если выигрывает только цена, но растёт число нарушений или нестабильность, это не доказательство экономии.
