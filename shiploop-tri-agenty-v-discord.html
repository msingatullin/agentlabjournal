Три AI-агента в Discord: от жалобы пользователя до проверенного pull request

Уровень: средний Время чтения: до 12 минут Формат: демонстрационный конвейер

AI-агент может быстро разобрать баг и подготовить исправление, но скорость не должна превращаться в бесконтрольный доступ к репозиторию. В этой статье соберём конвейер, где Discord принимает жалобу, триажер превращает её в задачу, фиксатор открывает pull request, а ревьюер проверяет изменения. Финальное решение о merge остаётся у человека.

Что строим

Представим небольшой проект с Git-репозиторием и тестами. Пользователь пишет в Discord: «После обновления профиль иногда сохраняется без часового пояса». Сообщение не должно сразу запускать изменение production-кода. Оно проходит через три независимые роли:

  1. Триажер уточняет симптомы, ищет релевантный участок кода и формулирует воспроизводимый issue.
  2. Фиксатор работает в отдельной ветке, в Docker-окружении и создаёт pull request.
  3. Ревьюер читает diff, запускает проверки и отмечает риски.

Важное ограничение: агенты не получают право напрямую сливать ветки, менять настройки репозитория или публиковать неподтверждённые заявления о результате.

Принцип сохранения решения за человеком: агент может подготовить материалы для решения, но кнопки merge и закрытия инцидента остаются у разработчика.

Архитектура конвейера

Discord здесь выступает входным каналом и журналом общения, GitHub — системой задач и изменений, Docker — границей воспроизводимого запуска. Связь между шагами лучше строить через явные статусы, а не через распознавание свободного текста. 

Discord #bugs
    │
    ▼
Триажер ──► GitHub Issue ──► подтверждение человека
                                      │
                                      ▼
                                Фиксатор
                                      │
                                      ▼
                          Pull Request + тесты
                                      │
                                      ▼
                                Ревьюер
                                      │
                                      ▼
                         решение человека: merge / доработка

Первый специальный термин — триаж. В нашем сценарии это не «автоматически починить всё», а классифицировать сообщение, собрать факты и определить следующий безопасный шаг.

Шаг 1. Подготовьте границы доступа

Для демонстрации достаточно тестового Discord-сервера, отдельного GitHub-репозитория или безопасной ветки и локального Docker. Не вставляйте токены в исходный код, сообщения Discord или команды, которые попадут в историю shell.

Минимальная матрица разрешений выглядит так:

Роль Читает Может изменять Не может
Триажер Discord, код, issues Черновик issue Коммитить и merge
Фиксатор Issue, ветку, тесты Отдельную ветку и PR Пушить в protected branch
Ревьюер Diff, логи, результаты тестов Комментарий к PR Одобрять merge от имени человека

Если проект использует защищённую основную ветку, включите обязательную проверку CI и запрет прямого push. Названия разрешений зависят от конфигурации GitHub и Discord; проверяйте их в интерфейсе перед запуском.

Шаг 2. Триажер превращает жалобу в задачу

Договоримся о формате сообщения. Пользователь должен по возможности указать ожидаемое поведение, фактический результат, шаги воспроизведения и окружение. Триажер не должен дополнять пропущенные факты догадками: неизвестные поля помечаются как «нужно уточнить». 

/bug
Ожидалось: профиль сохраняется с часовым поясом пользователя.
Получено: поле timezone иногда отсутствует.
Шаги: открыть настройки, изменить часовой пояс, нажать «Сохранить».
Окружение: неизвестно.

Результатом работы триажера становится структурированный черновик:

Заголовок: Профиль иногда сохраняется без timezone

Наблюдение:
- симптом подтверждён сообщением пользователя;
- окружение и частота пока неизвестны.

Гипотеза:
- обработчик сохранения может терять поле при частичном обновлении.

План проверки:
1. Найти обработчик профиля.
2. Проверить сериализацию и обновление поля timezone.
3. Воспроизвести сценарий тестом.
4. Не менять код до подтверждения issue.

На этом этапе человек проверяет формулировку и нажимает, например, «Создать issue». До подтверждения агент работает только с анализом. Это важная точка контроля: не каждый пользовательский текст является багом, а похожие симптомы могут требовать уточнения.

Шаг 3. Фиксатор работает в изолированной ветке

После подтверждения issue фиксатор получает только его идентификатор и разрешение на создание ветки. Перед изменением кода полезно зафиксировать чистое состояние рабочей копии и запуск базовых проверок. 

git status --short
git switch main
git pull --ff-only
docker compose run --rm app test

Команда тестов в примере условная: замените app test на команду, которая реально описана в вашем проекте. Не объявляйте проверку успешной, пока не видите её фактический код завершения и вывод.

Далее фиксатор создаёт ветку с понятным именем:

git switch -c fix/profile-timezone
# агент вносит минимальное изменение
git diff --check
git diff --stat
docker compose run --rm app test

Правило минимального diff помогает ревьюеру отличить исправление от случайного форматирования. Если для исправления нужен новый тест, фиксатор добавляет его рядом с существующими тестами, а не заменяет старые проверки.

После локальной проверки агент может подготовить коммит и pull request. В демонстрационном процессе это всё ещё действие с контролем: перед публикацией человек смотрит список изменяемых файлов и подтверждает push в удалённую ветку. 

git diff --check
git status --short
git add path/to/changed-file path/to/test-file
git commit -m "Fix profile timezone persistence"
git push --set-upstream origin fix/profile-timezone

Не используйте git add ., если агент не умеет надёжно объяснить каждый новый файл. Явный список путей снижает риск случайно отправить секреты, логи или локальные настройки.

Шаг 4. Ревьюер проверяет pull request

Ревьюер получает ссылку на PR и формирует короткий отчёт из четырёх частей: что изменилось, какие проверки прошли, какие риски остались и что нужно решить человеку.

Удобный порядок проверки:

  1. Сопоставить PR с исходным issue.
  2. Проверить, что diff ограничен заявленной проблемой.
  3. Посмотреть тест, который воспроизводит прежнее поведение.
  4. Проверить результаты Docker-команд и CI.
  5. Отдельно отметить неизвестные факты и непроверенные сценарии.
git fetch origin pull/123/head:review/pr-123
git switch review/pr-123
git diff origin/main...HEAD
docker compose run --rm app test

Номер 123 — пример, а не существующий pull request. Ревьюер не должен подменять отсутствующий результат фразой «всё прошло». Если контейнер не запускается или тесты не определены, это отдельное замечание к PR.

Пример комментария ревьюера:

Изменение ограничено сохранением timezone и добавляет проверку частичного обновления профиля. Локальная команда тестов завершилась успешно в указанном Docker-окружении. Не проверен сценарий миграции старых профилей; перед merge нужен ручной ответ владельца проекта.

После этого человек выбирает действие: одобрить merge, запросить доработку или закрыть PR. Бот может добавить label и сообщение в Discord, но не должен имитировать решение владельца кода.

Как связать Discord, GitHub и Docker

Практически удобно передавать между агентами не весь контекст канала, а компактный объект задания. Например: 

{
  "issue": "org/repo#123",
  "channel": "bugs",
  "requested_action": "prepare_fix",
  "branch": "fix/profile-timezone",
  "human_approval": true,
  "allowed_paths": [
    "src/profile",
    "tests/profile"
  ]
}

Поле human_approval должно появляться только после явного действия человека. Поле allowed_paths ограничивает область работы фиксатора и служит дополнительной проверкой перед созданием коммита.

Docker не делает код автоматически безопасным, но помогает повторить окружение. Запускайте контейнер с минимальными правами, не монтируйте домашний каталог разработчика и не передавайте в контейнер секреты без необходимости. Для команды, которая только анализирует код, сетевой доступ лучше отключать, если это совместимо с инструментами проекта.

Проверка результата

Конвейер считается демонстрационно готовым, если выполнены все условия:

  • жалоба появилась в выделенном Discord-канале;
  • триажер сформировал issue с отделёнными фактами и гипотезами;
  • человек подтвердил переход к исправлению;
  • фиксатор использовал отдельную ветку;
  • изменения прошли git diff --check и проектные тесты;
  • pull request содержит описание, ссылку на issue и результаты проверок;
  • ревьюер оставил проверяемый отчёт;
  • merge выполнен только человеком.

Для проверки отказоустойчивости специально отправьте неполную жалобу, измените тест так, чтобы он завершался ошибкой, и попробуйте добавить файл вне разрешённого пути. Во всех трёх случаях ожидаемый результат — остановка конвейера и понятное сообщение, а не попытка «дожать» процесс.

Типовые ошибки

Агент выдаёт гипотезу за факт

Разделяйте в сообщениях «наблюдение», «гипотезу» и «проверку». Формулировка «поле теряется в сериализаторе» допустима только после просмотра кода или лога. До этого пишите «возможная причина».

Триажер сразу создаёт много задач

Введите порог: issue создаётся только после подтверждения пользователя или ответственного разработчика. Иначе канал быстро заполнится дубликатами и предположениями.

Фиксатор меняет слишком много

Ограничьте разрешённые пути, требуйте статистику diff и проверяйте новые файлы перед коммитом. Большой diff — повод остановить процесс и вернуть PR на уточнение.

Ревьюер доверяет зелёному CI без чтения diff

Успешные тесты не доказывают, что исправлен именно нужный баг. Ревьюер должен сопоставлять изменение с issue и проверять, что тест действительно покрывает заявленный сценарий.

Секрет попадает в Discord или лог

Маскируйте токены, не выводите переменные окружения и не передавайте агенту больше секретов, чем требуется. Если секрет уже опубликован, его нужно отозвать и выпустить заново по правилам вашей инфраструктуры.

Ограничения демонстрации

Это учебная схема, а не готовая production-интеграция. В ней не описаны конкретные SDK, webhook-обработчики, схема аутентификации, политика хранения логов и резервный канал связи. Эти детали зависят от проекта и должны быть спроектированы отдельно.

Три агента также не устраняют необходимость в ответственном владельце кода. Они ускоряют сбор контекста и рутинную проверку, но не могут самостоятельно определить бизнес-приоритет, принять риск несовместимого изменения или подтвердить, что пользовательская проблема действительно закрыта.

Итог

Надёжный конвейер строится вокруг точек остановки: жалоба не становится issue без проверки, issue не становится кодом без подтверждения, код не становится merge без ревью. Discord даёт прозрачный вход, GitHub фиксирует историю решений, Docker делает проверки воспроизводимее, а ручной merge сохраняет ответственность за человеком.

Если вы проектируете похожий процесс с нуля, начните с трёх вещей: явной матрицы разрешений, формата задания между агентами и списка проверок, после которых человек принимает решение. Дополнительные практические материалы собраны в разделе guides.html, а термины — в glossary.html.
