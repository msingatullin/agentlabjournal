Инфраструктура Git для масштаба AI-агентов: кворумы ссылок и независимое масштабирование чтения

Массовая работа AI-агентов с Git-репозиториями ломается не только из-за объёма объектов. Главный конфликт возникает между двумя разными нагрузками: агентам нужно быстро читать множество веток и коммитов, а система должна надёжно принимать изменения ссылок. Если масштабировать их одной схемой репликации, чтение начинает зависеть от числа узлов, участвующих в записи.

Рабочая модель разделяет эти задачи. Ссылки репозитория — ветки, теги и другие refs — обновляются через per-reference quorum, то есть с отдельным требованием подтверждений для каждой ссылки. Git-объекты при этом хранятся в общем контентно-адресуемом объектном хранилище, а чтение обслуживается независимым пулом кэшей и read-only узлов.

Ментальная модель: refs — это состояние, объекты — история

Git разделяет указатели и содержимое. Ветка refs/heads/feature-a указывает на конкретный commit-id. Сам коммит ссылается на tree и родительские коммиты, а tree — на blobs. Поэтому обновление ветки — маленькая операция над метаданными, тогда как чтение рабочего дерева может потребовать цепочки объектов.

Для AI-агентов это особенно важно: сотни или тысячи параллельных задач часто читают одни и те же базовые коммиты, но создают отдельные временные ветки. Необязательно реплицировать каждый объект и каждую ссылку одинаковым образом. Надёжность refs и пропускную способность чтения следует проектировать как два независимых свойства.

Что означает кворум для отдельной ссылки

Пусть ссылка R имеет логическую версию v и указывает на commit-id C. Запрос обновления должен считаться успешным только после подтверждения кворума узлов, ответственных за R. Для разных ссылок можно выбирать разные политики:

  • Критические refs: большинство узлов или строгий кворум, чтобы не потерять продвижение основной ветки.
  • Эфемерные refs агентов: меньший кворум или асинхронная репликация, если их можно восстановить из задания.
  • Теги релизов: политика «создать один раз», запрет перезаписи и отдельная проверка полномочий.

Важна не арифметика сама по себе, а граница гарантии: клиенту нельзя возвращать успех до того, как выбранная политика для конкретной ref выполнена. Иначе агент может продолжить работу, а следующий запрос чтения попадёт в узел, который ещё не знает о новом состоянии.

Объектное хранилище как общий слой данных

Объекты Git удобно хранить в контентно-адресуемом слое: имя объекта определяется его хешем, поэтому одинаковые blobs, trees и commits естественным образом дедуплицируются. Read-узлу не требуется иметь полный локальный набор данных заранее: он может получить недостающий объект из объектного хранилища и положить его в локальный кэш.

Это не отменяет требований Git к целостности. Сервис должен проверять хеши полученных объектов, корректно обрабатывать pack-файлы и учитывать garbage collection. Удалять недостижимые объекты безопасно только после окна удержания, достаточного для задержавшихся refs, заданий агентов и фоновых операций.

Минимальная воспроизводимая модель

Ниже — локальный сценарий, который показывает разделение ссылок и объектов без привязки к конкретному продукту. Он не является полноценным кластером, но помогает проверить инварианты на обычном bare-репозитории.

1. Создайте источник и read-only копию

set -eu

workdir="$(mktemp -d)"
trap 'rm -rf "$workdir"' EXIT

git init --bare "$workdir/source.git"
git clone "$workdir/source.git" "$workdir/agent-a"

git -C "$workdir/agent-a" config user.name "Example Agent"
git -C "$workdir/agent-a" config user.email "agent@example.invalid"
printf '%s\n' 'base' > "$workdir/agent-a/README.md"
git -C "$workdir/agent-a" add README.md
git -C "$workdir/agent-a" commit -m "Create base"
git -C "$workdir/agent-a" push origin HEAD:refs/heads/main

git clone --bare "$workdir/source.git" "$workdir/read-1.git"

2. Создайте отдельную ссылку агента

git -C "$workdir/agent-a" switch -c agent/task-001
printf '%s\n' 'work' >> "$workdir/agent-a/README.md"
git -C "$workdir/agent-a" add README.md
git -C "$workdir/agent-a" commit -m "Agent task 001"
git -C "$workdir/agent-a" push origin HEAD:refs/heads/agents/task-001

В реальной системе этот push должен проходить через сервис refs: он проверяет полномочия, fast-forward-политику, версию ссылки и подтверждение кворума. Само наличие commit-id ещё не означает, что ссылка безопасно обновлена.

3. Проверьте, что read-узел видит ссылку

git --git-dir="$workdir/read-1.git" fetch "$workdir/source.git" \
  '+refs/heads/*:refs/remotes/source/*'

git --git-dir="$workdir/read-1.git" \
  show-ref refs/remotes/source/agents/task-001

git --git-dir="$workdir/read-1.git" \
  cat-file -t "$(git --git-dir="$workdir/read-1.git" \
  rev-parse refs/remotes/source/agents/task-001)"

Последняя команда должна вывести commit. Если read-узел получает ссылку раньше объектов, fetch обязан завершиться ошибкой или повторить загрузку, а не показывать частичное состояние агенту.

Как масштабировать чтение независимо

Read-путь можно увеличивать горизонтально: добавлять stateless-шлюзы, локальные кэши и read-only реплики. Они не должны самостоятельно принимать authoritative-решения об обновлении refs. Их задача — разрешить ссылку в commit-id, получить нужные объекты и вернуть согласованный снимок.

Практический read-path выглядит так:

  1. Запрос содержит имя репозитория и ref или commit-id.
  2. Шлюз читает ref из согласованного индекса или получает её версию из ref-сервиса.
  3. По commit-id разрешается граф объектов.
  4. Объекты берутся из локального кэша, затем из объектного хранилища.
  5. Ответ маркируется версией ref и, при необходимости, временем снимка.

Добавление read-узлов не должно увеличивать кворум записи. И наоборот, усиление кворума для main не должно требовать запуска новых копий всех pack-файлов. Это и есть независимое масштабирование чтения.

Проверка результата и наблюдаемость

Проверяйте не только HTTP-успех или код завершения Git. Для каждой ref полезно измерять:

  • версию ссылки и задержку между обновлением и появлением на read-узле;
  • долю чтений, обслуженных локальным кэшем;
  • время загрузки отсутствующих объектов;
  • число запросов, остановленных из-за отсутствующего объекта;
  • размер и возраст очереди репликации refs;
  • число объектов, доступных через ref, но ещё не подтверждённых объектным слоем.

Полезный контрольный инвариант: если read-узел сообщает ref версии v, все объекты, достижимые из её commit-id, должны быть доступны через согласованный read-path. Нарушение этого инварианта — сигнал к остановке выдачи снимка, а не повод скрыть ошибку повторной отдачей старой ветки.

Типовые ошибки

Один кворум для всего репозитория

Он упрощает модель, но связывает стоимость и задержку всех операций. Временная ветка агента начинает предъявлять те же требования, что и защищённая релизная ref.

Репликация refs без атомарной публикации объектов

Read-узел может увидеть новый commit-id, но не суметь получить его tree или blob. Публикация должна быть упорядочена: сначала доступность объектов, затем успешное обновление ссылки для чтения.

Слепое доверие к локальному кэшу

Кэш может быть устаревшим. Для запросов, где агенту нужен конкретный снимок, передавайте commit-id или минимально допустимую версию ref, а не только имя ветки.

Слишком ранний garbage collection

Недостижимый сегодня объект может быть нужен задержавшейся реплике, незавершённому заданию или ещё не опубликованной ссылке. Нужны retention-окно, журнал незавершённых публикаций и проверка достижимости.

Ограничения архитектуры

Per-reference quorum усложняет операции, затрагивающие несколько refs: например, атомарное согласование набора веток или миграцию репозитория. Для таких сценариев нужен транзакционный слой поверх отдельных обновлений либо явная модель снимка.

Объектное хранилище также становится критической зависимостью. Высокая доступность refs не компенсирует недоступность объектов. Нужны резервирование, контроль целостности, план восстановления и понятный режим деградации: какие чтения можно продолжить из кэша, а какие следует отклонить.

Наконец, кворум не решает проблему конфликтов в содержимом. Он подтверждает состояние ссылки, но не определяет, должен ли commit быть принят с точки зрения политики проекта, тестов или безопасности. Эти проверки остаются отдельным этапом write-path.

Итог

Git-инфраструктура для массовых AI-агентов должна разделять плоскость ссылок и плоскость объектов. Для refs задаётся политика per-reference quorum, соответствующая важности конкретной ветки или тега. Объекты размещаются в общем контентно-адресуемом слое, а чтение масштабируется отдельными read-узлами и кэшами.

Главный критерий корректности — не количество реплик, а согласованный снимок: видимая ref указывает на доступный и проверенный граф объектов. Если этот инвариант соблюдён, рост числа агентов можно обслуживать расширением read-пула, не превращая каждое увеличение чтения в изменение кворума записи.
