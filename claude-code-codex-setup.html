Как связать Claude Code и Codex для автоматизации проверок и вторых мнений

Claude Code удобно использовать как основной инструмент работы в репозитории, а Codex — как независимый контур проверки. В этой статье настроим вызов Codex из Claude Code через локальный скрипт и файлы обмена: без ручного копирования контекста, без передачи секретов и с понятным результатом проверки.

Что именно мы строим

Схема состоит из трёх частей:

  • Claude Code формирует задачу и сохраняет контекст в файл;
  • локальный скрипт запускает Codex CLI в отдельном процессе;
  • результат записывается в файл, который Claude Code может прочитать и обсудить.

Такой обмен можно назвать handoff — передачей задачи между агентами через явно определённый артефакт. Это не «магическая» синхронизация чатов: каждый запуск получает ровно тот контекст, который попал в файл.

Важно. Ниже приведён воспроизводимый шаблон. Названия CLI-опций могут отличаться между версиями, поэтому перед первым запуском проверьте локальную справку командами claude --help и codex --help.

1. Проверьте окружение

Сначала убедитесь, что оба CLI доступны в том же окружении, где запускается Claude Code:

command -v claude
command -v codex

claude --version
codex --version

Если одна из команд не найдена, установите соответствующий CLI по официальной инструкции вашей организации или используйте уже настроенное окружение. Не вставляйте токены в скрипт и не добавляйте их в репозиторий.

Перед интеграцией отдельно проверьте способ неинтерактивного запуска Codex:

codex --help
codex exec --help

В статье используется форма codex exec. Если в вашей версии используется другой подкомандный режим, измените только строку запуска в скрипте, сохранив файловый протокол.

2. Создайте безопасный формат контекста

Поместите служебный скрипт в каталог, который не содержит пользовательские секреты:

mkdir -p .claude/scripts .claude/reviews
touch .gitignore

Добавьте в .gitignore каталог с результатами, если проверки не должны попадать в Git:

.claude/reviews/
.claude/context/

Контекст лучше передавать в Markdown или обычном тексте. Для технического решения достаточно указать цель, ограничения, изменяемые файлы и вопросы для ревью. Не включайте в него:

  • значения переменных окружения;
  • токены, cookie и приватные ключи;
  • полные дампы баз данных;
  • файлы, которые не нужны для ответа.

3. Напишите прокси-скрипт для Codex

Создайте файл .claude/scripts/codex-second-opinion.sh со следующим содержимым:

#!/usr/bin/env bash
set -euo pipefail

input_file="${1:-.claude/context/request.md}"
output_file="${2:-.claude/reviews/codex-review.md}"

if [[ ! -f "$input_file" ]]; then
  echo "Не найден файл контекста: $input_file" >&2
  exit 1
fi

mkdir -p "$(dirname "$output_file")"

prompt="$(cat "$input_file")"

if [[ -z "${prompt//[[:space:]]/}" ]]; then
  echo "Файл контекста пуст: $input_file" >&2
  exit 1
fi

codex exec \
  "Проведи независимую техническую проверку материала ниже.

Требования к ответу:
1. Сначала дай краткий вердикт.
2. Затем перечисли найденные риски с приоритетом: высокий, средний или низкий.
3. Отделяй подтверждённые проблемы от предположений.
4. Если данных недостаточно, явно укажи, чего не хватает.
5. Не изменяй файлы и не выполняй разрушительные команды.

Материал для проверки:
$prompt" > "$output_file"

echo "Результат Codex сохранён в $output_file"

Сделайте файл исполняемым:

chmod 700 .claude/scripts/codex-second-opinion.sh

Права 700 — пример безопасного локального режима: запускать скрипт может только владелец файла. Если в команде используется общий рабочий каталог, согласуйте права с вашей политикой доступа.

4. Добавьте команду для Claude Code

Создайте команду Claude Code, например .claude/commands/codex-review.md:

Подготовь независимую проверку через Codex.

1. Определи, что именно нужно проверить: изображение, план или техническое решение.
2. Составь краткий контекст без секретов в файле:
   .claude/context/request.md
3. Включи в контекст:
   - цель;
   - исходные ограничения;
   - относящиеся к задаче файлы или пути;
   - конкретные вопросы для второго мнения.
4. Запусти:
   bash .claude/scripts/codex-second-opinion.sh
5. Прочитай:
   .claude/reviews/codex-review.md
6. Сопоставь вывод Codex с исходной задачей и перечисли действия, которые действительно нужно выполнить.

Не применяй изменения автоматически только на основании ответа Codex.

После этого в сессии Claude Code можно вызывать настроенную команду по её имени. Точное имя зависит от способа загрузки пользовательских команд в вашей версии Claude Code; проверьте список доступных команд локальной справкой.

5. Проверка изображений

Для проверки изображения сначала передайте Codex путь к локальному файлу и критерии оценки. Например, контекст может выглядеть так:

# Проверка изображения

Файл: /absolute/path/to/screenshot.png

Задача:
Проверь макет экрана регистрации.

Критерии:
- читаемость основного текста;
- достаточность контраста;
- соответствие указанной иерархии элементов;
- возможные проблемы адаптивности.

Ограничение:
Не делай выводов о пикселях, которых нет на изображении.

Поддержка передачи изображений зависит от версии Codex CLI и его режима запуска. Сначала проверьте опции в codex exec --help. Если CLI принимает изображение отдельным параметром, добавьте его в команду запуска после проверки синтаксиса. Если нет, используйте путь как ссылку на артефакт и попросите Claude Code подготовить текстовое описание изображения.

Не называйте изображение «проверенным», если Codex получил только его имя, но не получил содержимое или доступ к нему.

6. Проверка планов и технических решений

Второе мнение особенно полезно до начала реализации. Передавайте не весь репозиторий, а минимальный набор материалов:

# Техническое решение

Цель:
Добавить автоматическую проверку входящих webhook-событий.

Предложенный подход:
1. Проверять подпись запроса.
2. Сохранять идентификатор события.
3. Игнорировать повторную доставку.
4. Возвращать быстрый ответ и обрабатывать событие отдельно.

Проверь:
- полноту сценариев отказа;
- идемпотентность;
- границы доверия;
- риск утечки данных в логах;
- вопросы, которые нужно решить до реализации.

Так Codex выступает не источником истины, а независимым рецензентом. Окончательное решение принимает разработчик: вывод второго агента нужно сопоставить с кодом, требованиями и ограничениями проекта.

7. Проверьте результат вручную

Запустите скрипт на тестовом контексте:

mkdir -p .claude/context

cat > .claude/context/request.md <<'EOF'
Проверь этот короткий план как технический рецензент:
- какие предположения не подтверждены;
- какие риски следует проверить;
- какие данные нужны для окончательного решения.

План:
Сначала добавить в сервис новый обработчик, затем покрыть его тестами.
EOF

bash .claude/scripts/codex-second-opinion.sh

test -s .claude/reviews/codex-review.md
sed -n '1,160p' .claude/reviews/codex-review.md

Проверка считается успешной, если:

  • процесс завершается с кодом 0;
  • файл результата создан и не пуст;
  • в ответе есть вердикт и список рисков;
  • в контекст не попали секреты;
  • скрипт не изменил рабочие файлы.

Типовые ошибки

Codex не найден

Claude Code может запускаться с другим PATH, чем интерактивный терминал. Сравните вывод command -v codex в обычной оболочке и внутри той среды, где запускается команда. Не исправляйте проблему добавлением секретов в скрипт; сначала выровняйте окружение.

Результат пустой или обрезан

Уменьшите контекст до задачи, ограничений и конкретных вопросов. Большой дамп репозитория ухудшает независимую проверку и увеличивает риск передачи лишних данных.

Агенты повторяют одну и ту же ошибку

Добавьте в запрос явное требование искать контраргументы: «какое предположение здесь может быть неверным?» и «какой сценарий отказа не покрыт?». Второе мнение не становится независимым автоматически, если оба агента получают одинаково неполный контекст без критерия проверки.

Скрипт запускается из другого каталога

Используйте абсолютные пути или вычисляйте корень репозитория через Git. Для простого локального сценария достаточно запускать команду из корня проекта. Если команда вызывается из разных каталогов, замените относительные пути на проверенные абсолютные.

Ограничения схемы

Файловый handoff снижает ручную работу, но не решает все задачи интеграции. Он не гарантирует, что агенты одинаково понимают требования, не заменяет тесты и не подтверждает корректность результата. Кроме того, локальный скрипт не должен запускать автоматическое применение изменений, если это отдельно не проверено и не разрешено.

Для CI используйте отдельный режим с ограниченным контекстом, фиксированными версиями инструментов и явным контролем логов. Для локальной работы оставляйте результат ревью вне Git либо добавляйте его только после очистки чувствительных данных.

Итог

Практичная связка Claude Code и Codex строится вокруг простого контракта: Claude Code формирует запрос, скрипт передаёт его Codex, а результат возвращается в отдельный файл. Такой подход подходит для проверки изображений, планов и технических решений, сохраняет историю обмена и не требует ручного копирования длинного контекста.

Перед расширением автоматизации проверьте локальные справки CLI и зафиксируйте минимальные правила безопасности. Дополнительные материалы по рабочим процессам доступны в разделе гайдов, а термины — в глоссарии.
